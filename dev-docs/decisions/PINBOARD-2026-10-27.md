Owner: Cam; DESKTOP-ICONS-01 #64. Status: accepted implementation checkpoint,
subject to the early shaped-frame/input experiment in the tracker. This extends
R1's existing file-manager rank 3; no new release feature or mandatory dependency.
The user requested a substantial related batch after merged PR289 and completion

## Outcome and boundaries

Deliver the optional data-only pinboard: persistent references with independent
IDs, labels/named icons, saved snap-grid placement, pointer and keyboard actions,
monitor/work-area/scale recovery, restart and respectful desktop coexistence.
Unpin removes only a reference. There is no actual Desktop-directory mode,
file-job mutation action, automatic desktop takeover, default resident, second
wallpaper owner, database, new GUI toolkit, thumbnailing or per-workspace pin set.
Existing configuration formats and consumers stay usable.

One small native `FvwmPinboard` module owns the shaped X surface and interaction;
optional Go `fvwm-pinboard` owns data, bounded observation/icon/save/action work
and native coordination. Use ordinary Form dialogs for metadata and recovery.
A Form canvas would spread free-placement, picture and mixed-scale changes
through its accepted fixed-line/single-scale model. Buttons' fixed dynamic grid
and module-lifetime records also need broader surgery than this isolated canvas.
Reuse existing Module, FShape, property, Flocale, Colorset, Picture, monitor/scale,
collection, file-target and named-icon helpers. No new native packet type or
parallel core window-state authority. Keep the private message consumers together.

## Frozen records and ownership

Pin state is bounded JSON schema 1: revision, ordered pins and layout settings.
Each pin has a random independent 32-lowercase-hex ID, literal absolute target
bytes (JSON base64), display label, optional named icon override, preferred
monitor-name bytes and nonnegative logical grid column/row. IDs do not derive
from paths, observed directory IDs or a mutable position. Maximum 256 pins,
2 MiB serialized state, existing file-target path/name limits, 256 UTF-8 label
bytes and 256 monitor-name bytes. Reject duplicates, unknown schema, invalid
fields and overflow before publishing a model. Missing targets stay references.

Default layout: 96×96 logical-pixel cells, 32-pixel named icons and column-first
placement. Cell dimensions are configurable within 64–512 logical pixels and
icon size within 16–128. Existing monitor quarter-scale policy supplies actual
pixels; do not invent scale values. Persist monitor-relative grid coordinates.
Collision or absent-monitor fallback is deterministic and temporary; do not
rewrite a preferred placement merely because a monitor is absent. Reflow inside
checked work areas. Keep overflow references in a reachable paged Form manager;
a small primary-monitor management cell remains available even when no pin fits.
The board is sticky across desks/pages; workspace changes update work areas.

Create, relabel, move, unpin and reload operate on data only. One active save/
observation/icon/action job and no unbounded request queue. State writes use
private owned files, anchored checks, nonblocking locking, expected revisions and
atomic replacement. Failed/corrupt/conflicting saves retain the prior committed
model and report an explicit error; no silent replacement or unrequested merge.
Native entry IDs and callbacks belong to an exact view/topology generation.
Retired callbacks or worker results cannot mutate newer state or launch targets.
Closing/loss/restart cancels/reaps owned workers; launched applications retain
the existing explicit process-created handoff semantics.

Reuse the file model's observation/validation policy through a bounded single-
target helper; do not scan an entire parent merely to observe one pin. Root
folders, literal/invalid-UTF8 paths, symlinks, stale/missing/special targets and
unavailable configured openers receive explicit behavior/tests. Filesystem and
icon acquisition runs outside the native X owner. Named requests retain actual
scale/state/source identities; unavailable assets/formats leave usable labels.
Release old native pictures only after replacement, then retire only that
owner's acknowledged obsolete temporary image generation.

## Native transaction contract

The Go owner launches the native module through existing MFL/module transport
with an instance alias and random 32-hex owner token. Startup is explicit.
Commands and replies use ASCII tokens/strict decimal integers and lowercase
hexadecimal byte fields; `-` means an empty optional field. Each complete core
command, including its `SendToModule ALIAS` prefix, must fit the existing
1000-byte transport bound. Split entry fields instead of truncating a command.
Native staging is bounded to 256 entries; transaction generation is nonzero,
monotonic and at most 2147483647. Publish all-or-nothing; reject malformed,
duplicate, incomplete, stale or excessive records without changing the old view.

Messages to the instance (owner token is mandatory):

- `Owner TOKEN`: admits that owner and starts a 15-second lease. Startup waits
  at most five seconds for an owner/complete first scene before exiting.
- `Begin TOKEN OLD NEW COUNT`: prepares the next view from exactly OLD.
- `Layout TOKEN NEW CELL_WIDTH CELL_HEIGHT ICON_SIZE`: optionally stages
  validated layout dimensions inside the pending transaction. Omission inherits
  current/configured values; apply only with the matching Commit. This handles
  asynchronously loaded/saved layout without restarting the native instance.
- `Entry TOKEN NEW ID MONITOR_HEX COLUMN ROW MISSING`: records identity and
  preferred logical placement; MISSING is 0 or 1. An entry needs one Label.
- `Label TOKEN NEW ID UTF8_HEX`: at most 256 sanitized display bytes.
- `Picture TOKEN NEW ID PATH_HEX`: optional private resolved picture path,
  at most 384 bytes; unavailable/long pictures use label/type fallback.
- `Commit TOKEN NEW`: validates and swaps the complete scene/resources.
- `Abort TOKEN NEW`: drops only matching pending state.
- `Status TOKEN TAG`: replies after all preceding native records were consumed;
  use this actual native barrier at most every 32 submitted records.
- `Cells TOKEN TAG OFFSET LIMIT`: returns at most eight actual projected pin
  records for a generation-pinned icon acquisition.
- `Renew TOKEN`: refreshes the lease. `Retire TOKEN` releases only this canvas.

The parent launches `Module FvwmPinboard ALIAS` and supplies the token in Owner.
Instance configuration names are CellWidth, CellHeight, IconSize, Font and
Colorset, using ordinary FVWM module configuration before launch. Encoded Form
input may pass as literal Base64 in a generation-correlated Echo; decode it only
in the Go owner. Never evaluate it as FVWM/shell command source or include target
bytes in canvas records. The New pin dialog bounds its one Path field to 384
raw bytes with explicit refusal/guidance for longer inputs. Literal CLI/data
records retain the full existing file-target limit: `fvwm-pinboard --pin PATH`
is a data-only state edit and does not start/claim a canvas. An active board sees
external committed edits on explicit Reload; stale saves refuse by revision.
Do not split a user's path into implementation-level segmented input fields.

Normal FVWM configuration owns Font/Colorset and initial presentation defaults;
use existing parsing conventions. The Go CLI may explicitly supply these
settings through bounded equivalent instance configuration. Do not change
unrelated Form/Buttons syntax. Picture admission must not substitute labels or
paths into executable commands.

Native replies use core Echo text and no filesystem target bytes:
`FVWM_PINBOARD_STATUS TOKEN TAG CURRENT PENDING STATE WINDOW EPOCH`, where
STATE is ready/pending/refused/unavailable/retired and EPOCH is the current
16-hex MonitorUI epoch (zero only while unavailable). Events use
`FVWM_PINBOARD_EVENT TOKEN VIEW EPOCH VERB ID MONITOR_HEX COLUMN ROW`.
VERB is focus/open/context/move/manage/refresh/close/layout; `-` is an absent
ID/monitor and zero positions are unused for non-move events. Managed focus/
geometry actions use the shared command engine with the observed owned window.
`Cells` emits one `FVWM_PINBOARD_CELL TOKEN TAG VIEW EPOCH INDEX ID
MONITOR_HEX QUARTERS COLUMN ROW X Y WIDTH HEIGHT VISIBLE` per requested entry,
then `FVWM_PINBOARD_CELLS_END TOKEN TAG VIEW EPOCH OFFSET COUNT TOTAL`.
Indices follow the committed entry order; COUNT is the actual returned number,
TOTAL is the committed pin count and VISIBLE is 0 or 1. All entries in one reply
borrow one publication; reject/match view and epoch before acquisition. This
keeps native projection authoritative without duplicating its monitor policy.
A layout event causes fresh owner acquisition/publication for changed icon scale;
geometry and event coordinates remain actual pixels. Topology change aborts or
revalidates an in-progress drag; never persist a stale projection.

Projection and move previews also receive the actual root drawable bounds.
A visible pin must fit both its work area and that drawable. Off-root named
monitor preferences fall back without rewriting the saved monitor/grid values;
partially intersecting monitors retain their original grid anchor. Management
uses a drawable intersection, then another monitor or a bounded root recovery
cell. A named monitor's existence alone does not establish visible pixels.
Oversized pictures are cropped to their cell through explicit source/destination
rectangles; the existing opaque and alpha copy helpers can replace a caller's
GC clip, so restoring that clip after copying is insufficient.

Native drag/keyboard-move is a preview. Enter/release proposes a generation-bound
move; Escape restores committed placement. Go persists before publishing the new
scene. Tab/arrows/Home/End, Enter/Open and keyboard context actions have pointer
counterparts. Context/manager actions use static labels and typed IDs, never
filename-derived shell/FVWM commands. Support new pin, label/icon edit, unpin,
refresh/reload, move commit/cancel and explicit close/restart.

## X ownership and coexistence

Use one managed `_NET_WM_WINDOW_TYPE_DESKTOP` surface. Its bounding shape covers
only visible pin/management regions; holes expose existing root input/wallpaper.
Require SHAPE or return explicit unavailable; no opaque full-root fallback.
Before mapping, refuse an existing `_NET_DESKTOP_MANAGER_Sn` selection or other
desktop client. The selection is an interoperability convention, not a claimed
EWMH requirement. A strictly bounded X-only server-grab section may check/claim/
verify selection ownership; never perform filesystem work, wait for another
process or do unbounded client scans while grabbed. On selection loss or a
conflicting desktop appearance, unmap/release only this canvas and retain data.
EOF, retirement or expired owner lease also unmaps/releases ownership.

Startup must preserve existing focus, normal-client stacking, root bindings and
wallpaper properties. An initial InputHint=false is permitted to prevent the
core desktop default from grabbing startup focus; explicit keyboard entry then
uses core-managed focus after the canvas is ready. Prove this actual behavior,
including the frame's propagated shape, before relying on the architecture.
Use current MonitorUI epochs; associate legacy reservation samples locally and
discard them on topology replacement. No atomic reservation freshness claim.
A bounded work-area helper extraction may serve Form and Pinboard together,
with unchanged Form semantics and focused existing regression coverage.
