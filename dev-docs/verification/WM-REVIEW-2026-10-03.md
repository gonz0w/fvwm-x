# FVWM-X comparative window manager review

> Historical source links use repository paths. Original workstation line
> positions belonged to the dated checkout; consult the recorded source
> identity when reviewing that evidence.

Reviewed on 2026-10-03 for Linux, FreeBSD, and OpenBSD on AMD64 and ARM64.
The best next work is to fix IPC framing and geometry policy defects, then
replace modal input waits with an explicit interaction state. Deferred rendering,
bounded I/O, and selective removal of X round trips can follow without changing
the single-threaded ownership of X state or adding a compositor.

This is a source review and a proposed implementation sequence. Implementation
status now lives in [PROJECT-TRACKER.md](../PROJECT-TRACKER.md). Other window
managers were not benchmarked against FVWM-X. Observed source patterns do not
establish that an entire project is faster or more secure. No production code
was changed during this review.

## Window managers reviewed

from maintainer repositories; dwm was read from its official source browser.
Recommendations in the final column are our application of those patterns.

## Defects reproduced in FVWM-X

### MFL treats socket reads as commands

[client_read_cb](../../modules/FvwmMFL/FvwmMFL.c)
removes all currently buffered bytes and splits that chunk with strtok.
A Unix stream socket does not preserve command boundaries. In a private Xvfb
session using the current native Linux ARM64 binary:

- Sending `Echo unterminated` without a newline executed it immediately.
- Sending `Ec`, waiting 100 ms, then sending `ho split-command\n` lost the command.
- Sending an Echo command longer than the core's 1000-byte text limit closed
  both the offending connection and a separate healthy client connection. The
  WM remained running, but the module endpoint was removed.

The [core input limit](../../libs/defaults.h) is an existing
protection. MFL should reject an oversized client command before forwarding it
rather than making the core terminate the module.

**Recommended fix:** retain incomplete lines in the evbuffer, consume only
complete newline-delimited commands, reject embedded NULs, and enforce the core
text limit. Bound the number of commands processed per callback and arrange a
continuation when complete lines remain. Add per-client input/output budgets,
a connection limit, and a progress deadline. Reject or disconnect only the
responsible client.

**Verification:** split every byte boundary, multiple lines in one write,
missing delimiter, exact limit and one byte over, NULs, EOF with a partial line,
slow subscribers, concurrent clients, and responsiveness during a flood. Ensure
a healthy second client still works after the first is rejected.

### ConfigureRequest merging retains older values

In [_pred_merge_cr](../../fvwm/events.c), fields from the
older request overwrite fields already supplied by the newer request. A probe
compiled from the production function merged width 200 followed by width 300
into width 200. The same function returned 0 for WM_NORMAL_HINTS on the target
window, although its comment says this must stop merging: the atom comparison
is inverted.

This path runs when the motion method is no longer AutoDetect, including
explicit UseGravity/IgnoreGravity and successful autodetection. The probe proves
the policy defect; it is not a full X-visible integration result.

**Recommended fix:** carry an older field forward only when the newer request
omits it. Stop at relevant size-hint changes and preserve stacking, lifecycle,
and input ordering. Extract the decision into a pure helper before optimizing
queue traversal.

**Verification:** latest value wins, disjoint field masks combine, hints stop
coalescing, and sibling/stack requests retain order. Add real Xorg requests under
both explicit motion methods, including size hints, shade, maximize, and scale
transitions. Never coalesce across a monitor crossing merely to reduce work.

### Size-hint sanitization corrupts valid coordinates

[fev_sanitize_size_hints](../../libs/FEvent.c) tests the lower
coordinate bound with `>` instead of `<`. The extracted production function
changed x=123 and y=-42 to -32768. The wrapper
[FGetWMNormalHints](../../libs/FEvent.c) calls this sanitizer
on received hints. This is a confirmed policy error; its complete effect on
placement has not been measured in this review.

**Recommended fix:** preserve valid signed coordinates and clamp only values
outside the X protocol range. Consolidate repeated protocol range checks into
small typed helpers.

**Verification:** native tests at the limits, immediately outside them, zero,
and ordinary positive/negative coordinates; real client position/size hints on
Linux and BSD. Include negative monitor origins.

## Implementation priorities

These priorities combine the reproduced defects with source inspection.
Performance benefits beyond the previous event-batch measurements remain
hypotheses until measured.

| Order | Work | Existing gap and expected benefit | Acceptance evidence |
| --- | --- | --- | --- |
| 1 | MFL framing and bounded I/O | Reproduced framing loss; input allocation and subscriber output have no explicit budgets. Protect availability and preserve command semantics. | Fragmentation/overflow/slow-reader tests, healthy-client isolation, native BSD socket sessions. |
| 2 | Geometry normalization and coalescing | Reproduced older-value overwrite, missed hint barrier, and valid-coordinate corruption. Makes later optimization safe. | Pure policy tests plus real Xorg ConfigureRequest and hint cases. |
| 3 | Shared interaction state | [Move](../../fvwm/move_resize.c) and [Resize](../../fvwm/move_resize.c) wait through FMaskEvent outside the normal multiplexer. Background timers/modules and termination can be delayed. | Held-pointer timer/Echo tests, cancel, signal, destroy/unmap, hotplug, and grab release. |
| 4 | Deferred decoration and geometry updates | Repeated drawing/configuration can occur within one batch. A dirty region or dirty flag per owned UI object can combine superseded work. | Count X requests/redraws, compare latency and CPU; validate Expose, stacking, shading, and compositor interactions. |
| 5 | Reduce X round trips | [frame resize](../../fvwm/frame.c) synchronizes before resizing the parent. Startup interns many atoms separately. | Classify each barrier, test removal individually, batch atom initialization, measure startup and resize latency. |
| 6 | Bound property acquisition | [atom_get](../../fvwm/ewmh.c) requests 0x7fffffff units, then allocates/copies the reply and narrows its size to int. Image validation later does not bound this initial read. | Per-atom type/format/length limits; oversized and malformed properties; checked arithmetic and stable desktop under property floods. |
| 7 | Descriptor and child-process cleanup | [module launch](../../fvwm/module_list.c) creates ordinary pipes, applies close-on-exec later, logs failures without rejecting the module, and calls exit after failed child exec. | Descriptor-leak tests, failed exec, pipe setup failures, and unrelated-child EOF behavior. |
| 8 | Portable readiness polling | [main loop](../../fvwm/events.c) and synchronous module waits repeat fd_set construction and timeout logic. Modules are currently rejected above the select ceiling. | poll integration on all targets; high descriptors, EINTR, HUP, failed modules, preserved dispatch ordering. |
| 9 | Sandbox narrower processes first | Core configuration, session state, module spawning, and image/font loading need capabilities. MFL and future image decoders have narrower roles. | Native pledge/unveil or Capsicum checks that preserve reload, helpers, fonts, IPC, and restart. |

### Make MFL fully event driven

The socket already uses libevent, but callbacks invoke the synchronous
[ReadFvwmPacket and SendText helpers](../../libs/Module.c).
Those helpers assume complete blocking transfers. This checkout marks MFL
pipes nonblocking, so a fragmented read or EAGAIN can be mistaken for EOF;
SendText performs one write without handling a short result or EINTR/EAGAIN. MFL needs incremental module-packet
reception and queued nonblocking command output as well as socket framing.
The existing core module runtime is a useful model, not a reason to duplicate
its internals wholesale. Libevent provides [buffer watermarks and callbacks](https://libevent.org/libevent-book/Ref6_bufferevent.html),
but write watermarks alone are not an output-memory limit: enforce a byte budget.

The core already has incremental module framing, an 8 MiB output queue cap,
input lifetime pins, and bounded command/X dispatch. Preserve those protections.
A slow MFL subscriber should not grow memory indefinitely or stop every other
client. A timeout should refresh only on actual progress, following the reviewed
i3 output behavior.

### Keep interaction cancellation explicit

The proposed interaction record should own its mode, starting logical geometry,
pointer anchor, active window identity, grabs, and cancellation reason. Dispatch
motion, release, escape, destruction, and topology changes through one interface.
Resolve a window identity with a lifetime/generation check rather than retaining
an unchecked FvwmWindow pointer across arbitrary command execution.

Motion coalescing must deliver the last position before button release. Relevant
monitor crossings, hint changes, and lifecycle events are ordering barriers.
The proposal is to retain the existing 16-event cap and add bounded background
service during opaque interaction. Wireframe operations that grab the whole X
server require a separate policy: servicing commands while holding that grab can
create cross-process waits. Openbox's cancellation callback and Awesome's grab
callback provide useful models, but neither is a drop-in implementation.

The same audit should cover [WaitForButtonsUp](../../fvwm/events.c),
[PipeRead](../../fvwm/read.c), and
[synchronous module handshakes](../../fvwm/module_list.c).
PipeRead runs popen, reads command output, and waits in pclose in the core.
Move generation of expensive configuration/rules to a bounded helper process;
define ordering and continuation semantics before changing synchronous commands.

## Algorithms and cleanup worth testing

**Dirty regions and latest-value updates:** combine decoration invalidation and
superseded geometry changes within a bounded turn. Commit once before sleeping.
Skip a configure/redraw when the final state equals the already committed state.
Keep actual client ConfigureNotify feedback and causal event ordering correct.
This is a stronger candidate than adding a fixed 60 Hz throttle, which would
cap responsiveness on high-refresh displays and complicate final-release handling.

**Timer queues:** the current scheduler uses sorted linked insertion and scans
all queued jobs when executing due work. Bound overdue-command execution first.
Only replace it with a min-heap if timer-stress profiling shows material cost;
a heap needs deterministic equal-deadline order and efficient group cancellation,
so it can add complexity for the usual small queue.

**Elapsed-time budgets:** the 16-event cap already improved measured flood latency.
A count plus elapsed-time limit could bound a batch when individual handlers are
expensive. Measure its clock-check overhead and retain a count cap. One long
blocking handler must still be fixed at its source; a budget cannot preempt it.

**Protocol and ownership helpers:** extract mask merging, size-hint normalization,
checked property lengths, packet spans, and queue limits into narrow pure helpers.
Use one owner/cleanup path for grabs, pending I/O, and resource references. Keep
X queries and drawing in thin runtime adapters. Avoid a general-purpose object
framework or a wholesale language migration merely to shrink visible source.

**Selective asynchronous requests:** i3's [window-management path](https://github.com/i3/i3/blob/903bcd518df32b0e055b17f5da3f988a0187fd3d/src/manage.c)
issues several property cookies before collecting replies; Awesome similarly
batches startup queries. XCB's [request/reply model](https://xcb.freedesktop.org/tutorial/)
can hide round trips. Start with Xlib atom batching and cached known geometry.
Any XCB adoption must specify one event-queue owner, Xlib/Xft coexistence, error
handling, and BSD extension support. Changing APIs alone does not remove waits.

## Security and hardening boundaries

MFL currently verifies that its socket directory is owned by the current UID
and inaccessible to group/other users. The demonstrated socket defects concern
correctness and availability for callers that can access that endpoint; this
review does not establish remote code execution or a privilege escalation.
X client properties and decoded images remain separate inputs needing explicit
size, format, allocation, and work limits.

For process hygiene, create descriptors with close-on-exec where available,
keep flags intact in fallbacks, and fail module setup when required flags cannot
be applied. Clear close-on-exec only for the two module protocol descriptors
intentionally passed to its executable. Use _exit after failed child exec. Prefer
argv-based internal helper launches; preserve intentional user shell commands.
Audit lockfile ownership/type, no-follow handling, and listener close-on-exec.

OpenBSD [pledge](https://man.openbsd.org/pledge.2) and
[unveil](https://man.openbsd.org/unveil.2) should be staged after startup and
narrowed according to real operations. FreeBSD [Capsicum capability mode](https://man.freebsd.org/cgi/man.cgi?query=cap_enter&sektion=2)
restricts global namespace access, so cap_enter on the whole existing core would
conflict with runtime path lookup and launching programs. Start with MFL or an
image decoder that consumes pre-opened descriptors. Linux syscall restrictions
can be added to those same helpers after their interfaces are bounded. No helper
should gain authoritative X/window state.

The build already requests PIE, stack protection, and supported Linux fortify
flags. Audit actual ELF protections before adding linker flags. Add native
sanitizer/fuzz coverage for the extracted parsers and policies, including integer
overflow, truncated packets, malformed hints, huge properties, and client death.
Native Linux sanitizer CI remains unexecuted locally; the prior passing matrix
is not evidence of tests for these newly identified defects.

## Recommended next batches

1. Implement MFL line framing, reject over-limit commands per client, and add
   native live-X regressions for the reproduced failures. Then bound queues and
   replace its blocking module I/O.
2. Repair coordinate sanitization and ConfigureRequest merging with pure policy
   coverage and genuine X-visible requests under explicit motion methods.
3. Introduce a shared interaction state, first for opaque Move/Resize. Verify
   background responsiveness and lifetime cancellation before handling wireframe
   server grabs or changing synchronous configuration commands.
4. Measure dirty rendering and each X barrier independently. Fold proven wins
   into the Linux/BSD matrix, then tighten the narrow-process sandbox.

Large rewrites, threading authoritative X state, adding a compositor, replacing
floating policy with a tiling tree, and copying another WM's unlimited event
loop are poor fits for the current goals. The improvements above can be applied
incrementally while keeping modules isolated and the X state single-threaded.

## Review evidence

Local evidence is retained under ignored `builddir/wm-review/`:

- `reference/manifest.json` records repository revisions, URLs, file sizes,
  SHA256 hashes, and unavailable files. It contains 33 successful source/license
  snapshots across the seven projects, including the dwm HTML snapshot.
- `probe_mfl_stream.py` runs the controlled private-X MFL reproductions.
- `extracted_policy_probe.c` compiles the exact two inspected production
  functions with minimal X types/macros. It is diagnostic evidence, not a
  substitute for production-linked unit or nested-X integration coverage.
- `mfl-evidence.json` and `policy-evidence.json` retain the observed results.

The review fetched public source and ran a private native Linux ARM64 session.
It did not run other window managers or repeat the full BSD matrix, because it
made no production changes. Source ideas were evaluated independently; no
third-party implementation was copied into FVWM-X. Any future code reuse must
retain the applicable source license and attribution.
