== NAME

FvwmDesktop - FVWM-X baseline appearance and desktop services

== SYNOPSIS

Module FvwmDesktop

FvwmDesktop --check-config FILE [--json]

== DESCRIPTION

The sole shipped default configuration is the Slate desktop. Its layout is
shared by four palettes: Slate (teal), Dune (copper), Grove (green), and Ink
(blue). Each palette has matching light and dark colors and an original
wallpaper. Toolkit themes and settings are left alone.

The primary monitor has a flat top bar with application launcher, four
workspaces, window list, clock/calendar, status, appearance, and session
menus. Other monitors have no reserved bar space. Monitor topology events
rebuild the bar. Desktop workspaces are global and each has one page.

The centered launcher uses native FVWM menus with arrow-key navigation,
Enter, Escape and type-to-select. Search applications opens an input form
and then shows matching applications. It is a submitted search, rather than
a live fuzzy-search overlay. Discovery reads freedesktop desktop entries
without python-xdg, honors user overrides, Hidden, NoDisplay, OnlyShowIn,
NotShowIn and TryExec, and launches argument arrays rather than shell code.
Run command intentionally interprets the user's input with /bin/sh.

Files opens a native directory menu with folder navigation, a terminal
shortcut, and file opening. It shows up to 100 entries. An existing xdg-open
is used if available; otherwise files open in less in the configured terminal.
Calendar is a native month menu. Display information opens xrandr --query in
a terminal; this baseline does not yet include a graphical monitor editor.

== APPLICATION STARTUP ACTIVITY

Choose *Launch activity...* in the launcher, or send:

....
SendToModule FvwmDesktop launch-activity
....

The native form shows a read-only snapshot of startup notifications observed by
the window manager. Refresh requests a new snapshot; Close dismisses the form.
There is no periodic sampler. Pending means notification is in progress;
*Protocol ended* means a client sent a completion message; *Window observed*
means the core matched a managed window; *Expired* means no matching completion
was observed within sixty seconds. Protocol messages are public X11 data.
Protocol ended does not prove a successful exec, window map or completed task.
Launch submission alone does not prove those outcomes either. Actual launcher
exec errors retain their diagnostics; a crash after exec can appear as expiry.

The Applications menu, standalone desktop-menu actions and browser application
choosers share Desktop Entry startup metadata. `StartupNotify=false` disables
notification, including class fallback. True enables it; an absent key with a
valid StartupWMClass enables the legacy class case. Otherwise launch ordinarily.
The private *fvwm-startup-launch* helper announces through Xlib before replacing
itself with the literal application argument vector. It adds no resident watcher,
GUI dependency or session bus. Arguments, working directory and Terminal remain
those of the chosen application.

The helper allows at most two seconds for a separate announcement child, then
reaps it before exec. Missing helper, display failure, timeout or metadata outside
its bounds falls back to ordinary launch; stale inherited DESKTOP_STARTUP_ID is
cleared. The variable is set only after a successful announcement. Correlation
IDs use an unavailable event time of zero; startup activity does not change
focus or placement. A submitted launch is never automatically repeated.

Tracking has fixed bounds: 32 partial messages, 4096 bytes per message, 64 activity
records and 255 UTF-8 bytes per field. Partial messages expire after five seconds;
pending records after sixty. Terminal records remain for sixty seconds. Updates
do not extend a pending deadline. At capacity, applications still launch; excess
tracking is dropped and the view/query exposes counters. These deadlines use
monotonic time and run during idle and busy X activity.

The core matches a direct _NET_STARTUP_ID before a cached WM_HINTS window-group
ID at managed-window observation. Direct-ID and WM_HINTS changes are observed;
malformed direct IDs do not fall back to another identity. Class fallback needs
one unambiguous pending match and broadcasts its standard completion for other
observers. Direct/group properties accept one optional final NUL, while rejecting
embedded or double NULs. Late group-ID changes are observed for already managed
clients, including initially iconic clients. Group tracking is bounded to 256
client bindings and 256 leaders; additional tracking is refused and counted as
dropped when full. Unmanaged leaders retain only a reference-owned lifecycle
subscription while clients depend on them, with property observation during
pending launches. Last-reference release and destruction retire those claims;
existing window event interests remain intact. No inherited ID is written to a
client, and a destroyed leader cannot identify a later reused XID without a fresh
hints/lifecycle binding.
The *FvwmMFL*(1) `startups` query exposes the same bounded activity inventory.

== OPEN A FOLDER IN THE NATIVE BROWSER

Open *Files*, navigate to a folder, then choose *Open this folder in browser*.
The desktop passes that displayed folder to fvwm-file-browser(1). An idle
browser already displaying the same folder is refreshed and presented;
otherwise a new browser opens. Folder menus remain the default.

The action belongs to the displayed menu. If navigation has replaced that
menu, reopen Files and choose the action again. Folder names are passed as
literal arguments; the action does not open or execute entries in the folder.
The existing MIME defaults are unchanged.
Long Files-menu titles and entry labels use a shortened middle with an
ellipsis. Navigation and browser requests retain the full original paths.

The optional browser is found beside a development build or as the installed
*fvwm-file-browser* command on PATH. *FVWM_FILE_BROWSER* selects an explicit
executable instead. A missing browser,
failed launch or unsuccessful client exit produces a notice. A failed handoff
can have an unknown outcome: inspect the existing browser before trying again.
The desktop does not retry automatically. Starting a process does not establish
that its folder request completed; the browser reports loading or failure.

Up to eight browser launches can remain outstanding. A newly opened browser
has an ordinary application lifetime and can stay open after the desktop helper
restarts. Closing a browser releases its launch slot when its exit is observed.
This menu action does not require a session bus or a FileManager1 service.

== CONFIGURATION

Read the installed default-config/config to use the baseline. Normal FVWM
configuration lookup is unchanged; an existing personal config still wins.
The default reads $FVWM_USERDIR/local.config last for personal overrides.
No personal configurations are overwritten or removed.

Configuration examples for local.config:

....
*FvwmDesktop: palette slate
*FvwmDesktop: appearance auto
*FvwmDesktop: contrast normal
*FvwmDesktop: day 07:00
*FvwmDesktop: night 19:00
*FvwmDesktop: transparency on
*FvwmDesktop: motion off
*FvwmDesktop: keep_wallpaper off
*FvwmDesktop: wallpaper_palette follow
*FvwmDesktop: wallpaper_appearance follow
*FvwmDesktop: terminal xterm
....

Explicit module configuration overrides saved preferences for the module's
lifetime. The settings center reports these overrides. Changing or resetting a
saved choice does not remove an explicit module option; remove that option and
restart the helper to use the saved choice.
Omit an option to let the Appearance menu remember its selection. Times use
local 24-hour HH:MM format and must be different. A day interval may cross
midnight. Automatic appearance is checked each minute and immediately on
startup or after the clock catches up following resume. This uses a session
helper, so it needs no cron entries or access to another session's DISPLAY.
Manual Light or Dark overrides the schedule until Auto is selected again.

The Appearance menu saves preferences as private, atomic JSON in
$FVWM_USERDIR/desktop-state.json. This file is data only, never executed as
configuration. Palette choices preserve layout and bindings. Keep current
wallpaper prevents palette and day/night changes from replacing the active
wallpaper. The retained palette wallpaper choice survives session restarts.
Wallpaper palette and appearance can also be chosen independently. For example,
set wallpaper_palette to grove and wallpaper_appearance to light while keeping
the UI palette slate and appearance dark. The follow defaults use the UI palette
and its manual or scheduled appearance. Keep current wallpaper takes precedence:
new wallpaper choices are saved but do not replace the retained image until
retention is turned off. Custom image paths are not settings in this registry.
Custom wallpaper persistence remains the user's local.config responsibility.

Select *contrast high* for opaque high-contrast FVWM-owned controls. Dark
appearance uses black surfaces and white normal/disabled text and borders;
light appearance reverses them. The selected palette supplies the accent when
its contrast against the projected surface is at least 4.5:1; otherwise the
opposite black/white color is used. Selected text uses whichever of black or
white has greater contrast against that accent. Wallpaper and motion remain
independent. This mode does not recolor application contents or promise complete
accessibility support.

High contrast overrides presentation after module options are resolved. It
forces panels and menus opaque, retaining the requested transparency and launcher
opacity preferences. Selecting *contrast normal* restores those requests. For
example, these options keep a light Grove wallpaper with dark high-contrast UI:

....
*FvwmDesktop: appearance dark
*FvwmDesktop: contrast high
*FvwmDesktop: wallpaper_palette grove
*FvwmDesktop: wallpaper_appearance light
....


== DESKTOP SETTINGS

The Appearance menu's Desktop settings entry opens a native FVWM menu. The
same registry supplies the menus, validation and settings queries. This first
configuration-center covers these registered preferences:

* *palette*, appearance group: slate; choices slate, dune, grove, ink.
* *appearance*, appearance group: auto; choices light, dark, auto.
* *contrast*, appearance group: normal; choices normal, high.
* *keep_wallpaper*, appearance group: boolean, false.
* *wallpaper_palette*, wallpaper group: follow; choices follow, slate, dune,
  grove, ink.
* *wallpaper_appearance*, wallpaper group: follow; choices follow, light, dark.
* *day*, schedule group: local HH:MM, 07:00.
* *night*, schedule group: local HH:MM, 19:00.
* *transparency*, effects group: boolean, true.
* *motion*, effects group: boolean, false.
* *launcher_opacity*, effects group: integer percent, 0 through 100, default 94.
  It affects SlateLauncherStyle when transparency is enabled. Opaque mode
  presents 100% while retaining the saved percentage.

Times range from 00:00 to 23:59 and must differ. Use the schedule form or
the times command to change both together. Boolean set commands accept
true/false, on/off, yes/no or 1/0. Toggle changes the saved boolean choice.
Setting IDs and values map to fixed helper actions; they cannot contain FVWM
commands or resource paths. No focus, application or bar-layout settings are
registered in this checkpoint.

Each setting submenu shows its saved value, helper-effective value and source.
Saved means the helper's last successfully loaded or written snapshot; use
reload to adopt edits made outside the helper.
The effective value includes explicit *FvwmDesktop options. Application status
means the helper submitted its known commands to FVWM; it does not prove that
other modules have repainted. Later personal Style or Colorset commands cannot
be observed through this registry and are explicitly reported as unobserved.
The helper never rewrites personal FVWM configuration. Generic saved-setting
preview remains unavailable; native launcher-opacity and high-contrast previews
have their own timed confirmation paths described below.

Wallpaper query metadata includes resolved, resolution and composition_version.
Resolution is explicit, follow or retained. The resolved appearance can be auto:
that describes schedule policy, not the currently painted light/dark phase.
Retention reports wallpaper-retained as a runtime constraint. These fields remain
stable for the preference generation; clock-dependent painting still follows the
existing minute tick. Composition version 2 names the shared semantic color-role
projection, including high-contrast policy and is separate from the preference-file and IPC schema versions.
Transparency and launcher-opacity entries also expose resolved presentation and
resolution. Under high contrast they resolve to false and 100 respectively, with
resolution and runtime_constraint high-contrast. Their saved, effective and source
fields still describe the requested preferences and module overrides. In normal
mode, resolution requested uses the requested value; disabled transparency masks
launcher opacity with resolution/runtime_constraint transparency-disabled. These
fields describe the owner's submitted policy rather than an observed final paint.


Choose Edit saved preferences from Appearance or Desktop settings to open the
native grouped editor. It presents the registry's choices and time fields, with
explicit module overrides shown beside the affected setting. The fields edit
saved preferences; an override still determines that setting's effective value.
Opening the editor and changing fields have no effect on the desktop or file.

Apply (F3) validates the entire selected scope and saves it with one atomic
replacement, then submits the resulting theme and closes the editor. A bad
value or failed write preserves the draft, file and effective preferences; a
native notice explains the refusal. Tab moves between time fields; Return moves
to the next time field. Click Apply or press F3 to apply from either field.
Defaults (F2) replaces the selected scope's draft with registered defaults without
saving. Cancel, Escape, closing the window or its five-minute deadline discards
the draft. The deadline uses elapsed time and does not extend while editing.

Only one settings editor belongs to a helper. Opening another replaces it.
An accepted set, toggle, times, reset or reload retires the old editor; restarting
the helper closes any predecessor's Form. Callback tokens belong to that editor
and settings generation, so delayed actions cannot apply an old draft to newer
state. External saved-file edits are still checked at Apply: reload and reopen
the editor to adopt them. Query generation is an opaque snapshot identity that
changes on successful preference publication/reload and helper restart; it is
not an X-server generation or evidence that arbitrary FVWM commands were observed.

Reset accepts one setting ID, group:appearance, group:wallpaper, group:schedule, group:effects
or all. It changes only those saved preferences to registered defaults. It
retains explicit module overrides and the current wallpaper when the effective
keep_wallpaper choice requests it. A reset that would make day and night equal
is refused; reset group:schedule to restore both times. Reload rereads the saved
file, validates the combined configuration and reapplies the theme.

FvwmMFL also exposes correlated settings queries, typed set/reset/reload and
non-publishing validation. A validation returns the proposed saved/effective
values for the observed provider/generation without writing, submitting a theme,
closing an editor or changing the generation. It checks combined values and
overrides; it does not promise that a later write can acquire the lock or pass
the current saved-file revision check. It is available to read-only IPC clients.
See *FvwmMFL*(1) for the exact versioned request syntax and lifecycle rules.
Cancelling an IPC wait does not cancel this helper's submitted action; query
before replaying a change whose result was lost.

Writes validate the complete candidate and replace a private file atomically
before changing the helper's state or submitting theme commands. A failed write
preserves the previous file and in-memory choices. Cooperating writers use a
nonblocking lock; a changed file is refused until reload. This is not a
transaction across FVWM, arbitrary user programs or storage-device failure.

The state file is capped at 8192 bytes and must be a regular file owned by the
current user, with one link and no group/other permissions. Its immediate
directory must be owned by the user, must not be a symlink, and must not be
group/other writable. The final file and lock cannot be symlinks or FIFOs.
Existing directory ancestry remains the user's chosen trust boundary. A
persistent private .desktop-state.lock is normal. Temporary files are removed
on failure; source configuration and unrelated files are left alone.

Unversioned JSON from earlier helpers is read using the original normalization
rules. Complete schema_version 1 files load with launcher_opacity 94;
complete version 1 and 2 files gain follow defaults for the two wallpaper choices.
Complete versions 1 through 3 gain contrast normal. No file is rewritten on read.
The next successful save writes schema_version 4. Version 4 requires all eleven
preferences and retained wallpaper with valid types. Versions 1 through 3 require
their exact historical fields; incomplete or unknown fields are refused. Older
helpers cannot read version 4. Unknown versions, duplicate fields, oversized
or invalid files are preserved. Startup uses defaults and reports a persistence
error; repair the data file or move it aside, then use reload-settings. The
helper does not silently overwrite unreadable or future-version state.

Transparency is enabled by default: the bar uses a retained root wallpaper
with a strong tint, and menus use FVWM's snapshot translucency. This works
without a compositor. It does not show live windows through the bar, blur
backgrounds, or fade client windows. Opaque mode resets the bar to a solid
surface and disables menu translucency. Motion is off by default; enabling
it adds FVWM submenu repositioning and window-shade steps. These are native
FVWM effects, not compositor fades.

The panel height and generic font are available as InfoStore values
slate_height and slate_font. Override them in local.config before startup.
The frame defaults use a 28-pixel title and flat vector buttons; local Style
and TitleStyle commands can change these independently. No proprietary or
icon fonts are required. PNG wallpaper decoding uses FVWM's optional PNG
support; builds without it retain solid palette backgrounds.

The running settings owner also serves FvwmMFL's versioned `settings` queries
and provider/generation-checked `set`, scoped `reset` and `reload` actions.
This exposes
the same registry, saved/effective values, override precedence and private-file
revision checks used by the native editor. See FvwmMFL's STRUCTURED REQUESTS
section for the wire format, bounds and result meanings. A committed preference
or submitted FVWM command is not completed core rendering. Helper generations
do not observe external Style/Colorset state. Generic saved-preference preview
remains unavailable; the separate native consumers below use core-owned leases.
The `ipc-request` module message is reserved for that bounded literal-data
transport; existing `query-settings` Echo consumers remain supported.

== LAUNCHER OPACITY PREVIEW

Desktop settings offers *Preview launcher opacity...*, with 70%, 85%, 94% and
100% choices. The saved-value editor also accepts any integer 0 through 100.
Module configuration accepts *FvwmDesktop: launcher_opacity 94. A module override
or disabled transparency refuses saved-setting preview; change that source
first. High contrast refuses both saved-setting and runtime-only opacity preview,
including an editor draft selecting high contrast. A successfully saved/reloaded
high-contrast choice retires active or pending preview work before submitting
opaque presentation; failed validation or persistence preserves existing preview
state. Other menus retain their existing opacity policy.

The preview opens a native confirmation dialog. Open Applications to view the
candidate; close and reopen an already visible menu to sample its new opacity.
Within the core's 15-second lease, choose *Revert* (Escape), *Keep current value*
(F1, runtime only), or *Keep and save* (F2). Saving changes only launcher_opacity.
Revert, closing the dialog and expiry do not save. A later theme/configuration
update or restart can replace a runtime-only Keep; the saved preference is
reapplied by the normal theme path after reload/restart.

In a grouped editor containing opacity, *Preview opacity* (F4) captures the
complete validated draft and closes its old Form. Only opacity is previewed.
When the preview finishes, a new editor returns to that captured draft; other
fields stay unsaved. Keep and save commits only opacity before returning.
Queued old Apply/preview controls cannot publish, and changed settings discard
an outdated captured draft rather than rebasing it over newer preferences.

Keep and save checks helper/file freshness before applying the candidate and
again before confirmation. The core must confirm the lease before the private
file commit is attempted. The writer repeats its file-revision check under the
existing nonblocking lock. If writing then fails, the notice explicitly reports
*runtime opacity kept; preference was not saved*. Runtime confirmation and file
persistence are separate outcomes. Reload before retrying after file conflicts.
Saving does not replay the complete theme or overwrite a newer external core
command. Rendering after confirmation remains unobserved.

The core owns the exact previous scalar, conditional apply and monotonic
deadline. Intervening tracked appearance activity conservatively refuses
restoration; inspect current appearance before retrying. Helper death recovers
without waiting for the dialog. An independent 16-second native Form timeout
closes an orphaned preview consumer without confirming or saving.

The helper retains one bounded reply wait, one captured draft and at most one
queued control, with Revert taking precedence. Instance/view tokens isolate stale
callbacks. One stale-start retry obtains a fresh generation and still applies
conditionally. Active status polls once per second. Missing/invalid replies
abandon and report uncertainty. Recovery runs at eligible core service points,
including interactions; it cannot preempt one blocking call or a stalled server.
Existing displayed menu pixels can require reopening.

The existing preview-opacity module command and FvwmMFL's core `preview`
resource remain runtime-only. Registry `preview: false` still declines generic
IPC saved-preference preview; `native_preview: true` identifies the opacity
consumer. General appearance/image-resource preview remains open.

== HIGH CONTRAST PREVIEW

Choose *Preview high contrast...* in Desktop settings, or *Preview high contrast*
(F5) in an editor containing contrast. This previews `contrast=high` from the
current normal presentation. It uses the current palette and appearance, not
unapplied palette or appearance fields in the editor. Other draft fields return
to the editor unchanged after the preview. The requested transparency and
launcher opacity values remain intact; high contrast resolves them to opaque
presentation and 100 percent opacity.

The *Preview high contrast* dialog offers *Save* (Enter) and *Cancel* (Escape)
within the core's 15-second active lease. Save first confirms the runtime
resources, then saves only `contrast`. Cancel, timeout or loss of the settings
owner requests recovery without saving. Closing the dialog leaves recovery
to the core deadline. A menu or other interaction can defer resource recovery
until the command stack unwinds;
the pending state does not claim that old pixels are already restored.

The core retains actual color, image and shape owners for fourteen shared roles
and the two affected menu opacity values. Recovery restores those resources
instead of reloading their filenames. Wallpaper, motion, fonts, icon choices
and unrelated menu-style properties are outside this preview. Modules repaint
independently; runtime confirmation is not a simultaneous repaint guarantee.

An overridden contrast, current high contrast, stale settings/file revision or
another preview refuses admission. Pending or unsupported image owners, raw root
pixmaps, ParentRelative backgrounds, ownerless masks, foreground/background tint
and nonopaque foreground alpha also refuse this resource scope. Existing
configuration remains usable. Resolve the refusal before opening a new preview;
there is no fallback that replays theme commands.

An intervening tracked Colorset, MenuStyle, style or root-image change refuses
restoration rather than overwriting the newer state. If the core has already
confirmed but saving fails or an external preference edit wins, the notice says
that runtime high contrast was kept and the preference was not saved. Settings
report `source: runtime-kept-preference-unsaved`; schedule ticks and unrelated
preference edits retain that runtime choice. An explicit contrast edit or reload
replaces it. Reload before intentionally retrying a conflicting file write.

The contrast registry entry reports `native_preview: true` for this conditional
consumer. Generic settings `preview: false` remains unchanged. Reverse contrast,
general transparency and other appearance/resource previews remain unavailable.

== CONFIGURATION INSPECTOR

Choose *Configuration inspector...* from Appearance or Desktop settings, or use:

....
SendToModule FvwmDesktop inspect all
SendToModule FvwmDesktop inspect settings
....

The opt-in native viewer is read-only. Its scopes are *all*, *settings*, *theme*,
*bindings*, *layout*, *sources* and *commands*. Select a scope and enter a literal
case-insensitive filter, then Apply (Enter). F1/F2 move between pages, F5 refreshes,
and Escape or the titlebar close button closes the view. Its own Form requests
keyboard focus and releases it on close; normal FVWM focus override policy still
applies. Closing retires its view
identity; a delayed worker response cannot reopen it. Paging does not recollect
or execute an inspected action.

Settings come from the current registry and owner snapshot, including saved and
requested effective values, source class, high-contrast/retained-wallpaper
constraints and known submitted state. Theme rows distinguish the provider's
semantic role projection from the core's observed colorset, menu and decor
definitions. Scheduled appearance is captured provider policy, not a claim about
current painted pixels. Bindings show bounded active global, menu, fallback,
placement and modifier/context policy. Their free-form action arguments and
window match text are hidden. Commands use the same generated core inventory as
FvwmPrompt completion; arbitrary command argument grammar is not inferred.

Layout coverage is monitor/workspace/work-area and scale metadata in actual X11
pixels. Per-widget bounds and effective per-window style attribution are
unavailable here. Literal source observations reuse the configuration checker's
Read/include traversal and setting registry. They show bounded file/line spans
and include context; home paths are shortened. Traversal order and matching
values do not prove which file supplied runtime state. Dynamic constructs remain
unchecked. The ordinary configuration-check JSON schema is unchanged.

The viewer does not start FvwmMFL. Without it, local settings/source/command
inventory remains available while core-query sections explain their missing
provider. Each collection uses bounded read-only requests, with read-only mode
admitted on the same connection before a query. Separate sections are
point-in-time observations, not an atomic desktop snapshot. Provider loss and
changed generations are reported on refresh; the viewer does not continuously
watch every domain.

A refresh replaces the displayed snapshot only after validation. Failure retains
the previous data with a stale notice; one running collection can coalesce one
additional refresh. Filters are limited to 128 UTF-8 bytes. Collected rows and
query work are capped, with explicit truncation/partial reasons. Filtering a
bounded core inventory cannot establish absence outside its collected range;
command-name filtering searches the generated command inventory before its row
cap. No personal configuration, preference file or inspected command is changed.

== CONFIGURATION CHECK

Desktop settings offers Check local.config. It reads
$FVWM_USERDIR/local.config in a bounded worker and presents a native report.
F1/F2 move between report pages; Escape closes the report. Source locations
include physical start/end lines for continued logical lines and the immediate
Read caller. Long paths are shortened for the native view. A new report replaces
the previous snapshot; callbacks from an older report cannot select its pages.

The check never executes configuration, starts modules, applies preferences,
expands variables or runs PipeRead, shell commands, functions or Lua. It checks
only literal colon-form *FvwmDesktop options for the registered settings,
plus literal Read filenames with optional Quiet. Boolean/time/enum validation
uses the same preference registry as the running helper. Explicit day/night
values must differ when both appear. Saved preferences are not loaded, so this
does not validate their combined effective runtime state.

Comments and blank lines are ignored. A backslash immediately before a newline
joins physical lines, as in FVWM's reader. Directive recognition and Read
separators use ASCII whitespace. Desktop options reuse the running helper's
existing trimming and literal-space option split. Input is UTF-8; other encodings
are reported as unchecked. NUL bytes are errors.

Literal Read searches FVWM_USERDIR, FVWM_DATADIR and the checker's working
directory, in that order, or uses an absolute path directly. It is not relative
to the including file. Quiet permits a missing optional file; it does not hide
an unreadable or nonregular source. Symbolic links are followed; device/inode
identity detects active Read cycles. Repeated nonrecursive reads remain allowed.
This is a fixed search-root snapshot, not a simulation of executable commands
that could change paths, variables or generated files.

Other FVWM commands, custom function calls, module options, terminal invocation,
expansions, escaped filenames and unsupported Read syntax are reported as
unchecked. They may be valid configuration. This first checker is not a full
FVWM syntax validator or a predictor of session startup; general core-command
argument/source diagnostics remain separate work. No configuration migration
or new desktop package is required.

For a complete source/include chain and observed file hashes, invoke the installed
helper directly outside FVWM, without an X display:

....
/path/to/FvwmDesktop --check-config "$HOME/.fvwm/local.config"
/path/to/FvwmDesktop --check-config "$HOME/.fvwm/local.config" --json
....

Use the helper in the configured ModulePath; it is normally installed in the
versioned libexec module directory. Text output escapes control characters in
paths. JSON schema_version 1 reports coverage, status, checked_directives,
errors, unchecked, observed files with SHA-256 hashes, and diagnostics. Each
diagnostic has path, line, end_line, included_from, severity, code, message and
parser. Included callers retain their own start/end lines. The file hashes
identify bytes read, not an atomic cross-file or future runtime snapshot.

Exit status 0 means the supported subset has no reported errors or unchecked
constructs. Status 1 means a supported-value or source-read error. Status 2
means incomplete coverage, an exhausted budget or CLI usage error. A zero exit
does not certify arbitrary FVWM configuration or effective runtime settings.

One check reads at most 4 MiB combined, 64 file visits, eight active file levels,
10,000 physical lines, 1 MiB per logical line and 64 diagnostics. Reaching a cap
reports incomplete checking. An elapsed three-second budget is checked between
reads/lines; it cannot preempt an individual filesystem call. Sources must be
regular files and are opened without blocking on FIFOs. No check writes a source
or preference file. The helper admits one check at a time within its existing
bounded worker pool and retains one result snapshot. Source walking and
diagnostics use the shared Go settings registry in the private worker; complete
reports are validated before the resident controller presents them.

== RUNTIME CONFIGURATION DIAGNOSTICS

Invalid registered *FvwmDesktop settings and unknown desktop options produce a
native notice and a stderr diagnostic during initial configuration, retained
configuration replay and live configuration delivery. The notice uses the
existing FvwmForm viewer (title "FVWM-X"). Initial configuration applies valid
settings through the existing override and settings-generation rules. After
startup, newly delivered options are validated for diagnostics only: they do
not change overrides, effective settings or terminal selection. Valid configured
changes still require restarting FvwmDesktop to take effect.

When the core supplies a file context, the diagnostic shows its complete path
and physical first-last line span, followed by the complete root-first nested
Read chain and each caller's span. Generated configuration and invocation
context are identified explicitly. Their optional location is the nearest known
enclosing invocation and may be an outer call; intervening dynamic steps are
not reconstructed. It is not an exact direct inner call or definition location.
Missing or rejected metadata displays "Source context unavailable".
This is diagnostic context for a delivered desktop option, not an inventory of
effective bindings or theme origins. Aggregate settings errors without a
single attributable option do not claim a source location.

FvwmDesktop selects live configuration delivery with M_SENDCONFIG and the
optional native MX_CONFIG_SOURCE extended packet alongside existing core replies.
It accepts one version-1 source record of at most 1536 UTF-8 bytes and sixteen include callers. Only the immediately
following configuration packet with the same nonzero opaque key can consume
that record. Intervening packets, mismatches, malformed/ambiguous fields,
invalid Unicode, controls in source fields, and exhausted bounds discard the
context. Source text is never executed, replayed as a command or offered as an
editable action. Modules that do not select this packet retain their ordinary
configuration stream.

Native notices and configuration-check source rows use literal TextHex text,
wrapped at 72 Unicode characters. Quotes, dollar signs, percent signs,
backslashes and non-ASCII paths are preserved. The checker displays complete
paths and include chains across continuation pages of at most twelve wrapped
source/message rows, keeping Close and navigation controls within the viewer.
Controls in checker paths are visibly escaped. The
offline text report also preserves continuation spans on included callers;
JSON schema_version remains 1.

== DESKTOP SERVICES

The resident desktop controller is a Go executable. It owns preference-file
commits, settings revisions/generations, editor and preview lifetimes, module
publication and desktop-service coordination. It imports the shared settings
registry and native UI plans directly; settings actions need no policy
subprocess or scalar cache. Complete candidate validation precedes a file
commit or editor replacement. Failed validation or persistence keeps the
editable draft. A successful atomic rename remains committed even if later
module publication fails.

The adjacent private *fvwm-desktop-worker* owns application discovery, system
metrics, audio/power jobs, bounded folder-menu listings and read-only
configuration checking. Its results remain data; it cannot commit preferences
or own a preview lease. The separate native *fvwm-desktop-capture* helper owns its Xlib connection and
uses the selected libpng dependency. No installed desktop controller/helper
requires Python. Build/generation/test tooling retains its separate migration
scope. Installed users need no Go compiler, pip package, additional GUI toolkit
or compositor.

Only the resident event loop changes controller state or writes the module
pipe. At most four service jobs are admitted, with two running at once. Pending
input and output each have a 1 MiB bound; partial native packets and command
writes retain their order. Shutdown cancels supervised jobs. Preference writes
use a nonblocking lock and directory-relative private-file operations; a
conflicting external edit requires reload. There is no second settings service.
Explicit Run input remains the intentional shell action; application/terminal
arguments are literal. At most 256 applications launched by this controller can
remain running at once; a full launch limit reports a notice.

Each nonresident Go job accepts at most 64 KiB of JSON and returns at most
1 MiB. Backend output is capped at 64 KiB. Go checks a four-second job context
and one-second query/three-second power deadlines; the controller supervises
request/output progress with a six-second deadline. Capture has a separate
30-second deadline and a 4096-byte textual result limit.
A stalled job or inherited pipe is retired with its owned process group. A
filesystem syscall still depends on operating-system cancellation; these are
bounded service policies, not a hard real-time guarantee.

Application discovery searches XDG_DATA_HOME (default ~/.local/share), then
XDG_DATA_DIRS (default /usr/local/share:/usr/share), in priority order. Relative
environment roots are excluded; explicit roots remain available. A hidden or
invalid entry at higher priority masks the same desktop ID in lower roots.
Discovery uses localized names and optional icons, typed visibility and terminal
metadata, current-desktop and executable-availability filters, and decoded paths.
Localized icons require a base Icon value.
Desktop visibility uses the colon-separated XDG_CURRENT_DESKTOP value, falling
back to FVWM when it is empty.
Locale selection uses LC_ALL, LC_MESSAGES and LANG in that order, with LANGUAGE
preferences before the selected locale. C, C.* or POSIX suppresses LANGUAGE.
A specified working directory must be absolute, at most 4096 bytes and an
existing directory.
The shared Desktop Entry reader rejects malformed or duplicate keys, NUL and
invalid UTF-8. The shared Desktop Entry Exec parser expands field codes into
literal arguments and refuses malformed field codes or quoting; it does not
invoke a shell.

Declared Desktop Actions appear as additional *Application — Action* rows, with
localized labels. Only the first eight declared IDs are considered; invalid,
duplicate or missing actions still occupy positions in that limit. They use the
parent application's working directory, terminal setting and name and desktop
file for %c and %k. An optional action icon overrides the localized parent icon
for %i; otherwise the parent icon is used.
Each launches as a literal argument vector. A malformed action is refused independently and does
not remove a valid primary launcher; unlisted action groups are not launched.
Actions share existing result limits, pagination and generation-bound callbacks.
Each job caps directory roots at 64, enumeration at
8192 entries, depth at 16, candidates at 2048 per root and results at 512.
Depth and candidate/application count caps limit the selected list. Enumeration
or encoded-result overflow reports a failed refresh; a failed refresh preserves
the previous published snapshot. Application rows in both the launcher and the
last submitted search become Greyed until a fresh discovery succeeds; the search
menu is updated without reopening it. Repeated discover requests during a job
retain one latest pending request and discard the superseded result.
The existing explicit Run command/shell behavior is unchanged.

Settings, applications and system menus use three fixed in-process bindings.
Settings follow the controller's committed generation. Worker bindings track
admitted request intents; admission alone does not establish data availability.
Only a validated result from the current request and controller lifetime can
replace the working snapshot. Equal rendered menus emit no replacement commands;
obsolete application pages are retired. Generated application rows carry the
controller lifetime and published application generation. A delayed row from an
older or reordered snapshot is refused rather than launching its former index
against new data. Module-owned menus install a bounded popdown callback before
their first display. If core refused an update while the menu was mapped, closing
the menu retries its latest desired projection (or retires an obsolete page).
An unchanged projection needs no retry. This uses the existing native popdown
action and adds no polling timer. The public
*launch index* command remains available. Narrow settings scopes change the
settings root while retaining the complete bounded submenu inventory used by
Appearance and other settings popups. Reload closes the worker bindings and
requests fresh snapshots, so delayed results cannot revive a prior lifetime.

Before the first status result, and after status collection fails, the system
menu reports unavailable status and disables worker-backed sound and power
controls. Last working status remains available as explicitly old data. Lock,
logout and other independent local actions retain their own availability checks.
A fresh status result restores the worker-backed controls; it does not establish
that a later sound or power action succeeded. The existing shared five-second
status sampler remains active; bindings add no polling timer or settings service.

The installed helper is next to FvwmDesktop; build-tree consumers use the sibling
Go output. Developers may set FVWM_FILE_BROWSER to an explicit browser
executable for the Files-menu action; missing optional peers do not prevent
desktop startup. Developers may set FVWM_DESKTOP_WORKER to an explicit helper path for
isolated tests. The one-shot JSON protocol is internal, not a user configuration
format. Module queues, packets and generated menus remain bounded; child programs
do not inherit the module protocol descriptors.

Linux CPU/RAM counters come from /proc, and battery/link state from /sys.
FreeBSD and OpenBSD counters use sysctl and base utilities. RAM accounting is
used RAM including caches on BSD, and excludes available/reclaimable RAM on
Linux; the values are not directly comparable. Network status reports active
interfaces, not a guarantee of Internet access. Missing sensors show as not
reported; no battery is fabricated for a desktop machine.

Sound keys and menu actions use sndioctl on OpenBSD, mixer on FreeBSD, or an
already installed amixer on Linux. If the backend is absent, the sound menu
is disabled. Network information uses ifconfig or an existing ip command.
Settings needing privileges remain the operating system's responsibility.
No helper automatically invokes sudo or doas.

Power requests have their own bounded admission slot; an audio job cannot silently
replace them. Duplicate or capacity-limited requests report that no additional
request was sent. Backend authorization and errors remain with the operating
system. A pending locker invocation refuses duplicates within this controller
instance; construction or unsuccessful exit reports unconfirmed protection.
Starting a locker is not proof that the screen is locked. Detached lockers and
applications retain their existing lifetime across controller/WM retirement;
there is no lock-before-sleep or full session-service readiness guarantee.

Screenshots use Xlib and the configured libpng library in the separately
supervised native capture helper. A PNG-disabled build immediately reports
capture as unavailable. Failed writes remove the helper's newly created partial file.
Print captures the root display to ~/Pictures/Screenshots with a unique,
private filename. Capture supports TrueColor visuals and a maximum of 16
megapixels. The capture runs independently of the WM and does not include the
pointer cursor. A small native message announces the saved file or an error.
These messages report FVWM desktop actions; the helper is not a freedesktop
D-Bus application-notification server.

A terminal is detected from xterm, uxterm, or rxvt. Set FVWM_TERMINAL or the
terminal option for another command. Terminal tools require a compatible
-e option; no terminal is installed automatically.

Lock delegates only to an existing xlock or slock. If neither is available,
the Session menu disables Lock and a keyboard request explicitly reports
that the screen has NOT been locked. No decorative lock window is presented
as a security boundary. A portable bundled authentication locker remains
separate work. Power off and reboot require confirmation and use existing
session permissions; denied requests are reported. Log out quits FVWM;
Restart FVWM reloads it without closing application windows.

== REMOTE COMMANDS

SendToModule FvwmDesktop accepts these commands:

....
set palette slate|dune|grove|ink
set appearance light|dark|auto
times 07:00 19:00
toggle transparency
toggle motion
toggle keep_wallpaper
set wallpaper_palette follow|slate|dune|grove|ink
set contrast normal|high
set wallpaper_appearance follow|light|dark
settings [all|setting-ID|group:appearance|group:wallpaper|group:schedule|group:effects]
preview-setting helper-instance opacity-percent
edit-settings [scope]
check-config
palette
palette-state token
query-settings token [scope]
reset scope
reload-settings
refresh
discover
barrier token
terminal
files
calendar
screenshot
....

refresh reapplies the current theme and restores the clock/workspace display
after a bar rebuild. discover refreshes installed applications. A desktop
helper belongs to one FVWM session and has no network listener. barrier emits
Echo token after earlier helper commands reach FVWM. Tokens contain at most
64 letters, digits, underscores or hyphens. This orders command application;
independent modules may still be repainting.

The explicit diagnostic command *bindings token* emits three
*Echo FVWM_BINDINGS_1 token domain hex-json* records, one each for the fixed
settings/apps/system domains. Every record fits the 1000-byte native command
limit, and all three records are validated before any are submitted. The token
follows the same bounded identifier syntax as barrier. Decoding each domain's
hexadecimal JSON yields its binding policy state, counters, pending/in-flight flags,
source/identity bounds, data availability and retained menu counts. It contains
no settings values or application data. Reading the diagnostic does not refresh,
invalidate or publish a view, and normal operation emits no diagnostic records.
The shared status sampler can still advance its domain every five seconds.

settings opens the native configuration-center menu for the requested scope.
edit-settings opens the grouped saved-preference editor for the same scopes.
check-config starts the non-executing local.config check and accepts no module
arguments. The native report generates token-bound check-page callbacks;
ordinary clients should request a new check instead of reusing those callbacks.
The editor's apply-settings, defaults-settings and cancel-settings callbacks
carry an opaque per-instance token and are generated by the helper; ordinary
command clients should use the documented set, times, reset or reload commands.
query-settings emits one Echo message per registered setting and a final
completion message through the existing module transport. A token has 1 to 64
letters, digits, underscores or hyphens. Replies have this form:

....
desktop-settings-token setting-ID {JSON metadata and state}
desktop-settings-token done
....

Metadata includes type, default, choices or time bounds, description, group,
owner, capability, availability and preview support. State includes saved,
effective, source, application, generation and persistence_error. Each reply fits the
existing core command limit. Refused operations show a native notice and leave
the prior settings intact; this query is not the future general IPC result API.
persistence_error reports a startup read problem that blocks saving until a
successful reload; individual operation errors are reported by the notice.

The structured FvwmMFL `provider` query reports this helper's preference
configuration readiness, supported operations and known persistence error.
Optional provider watches announce readiness and changed preference generations
without broadcasting values. Conditional settings queries return unchanged
when the exact targeted preference generation matches. These interfaces do not
manage session services or confirm theme application; see *FvwmMFL*(1) for
framing, limits, stale identities and snapshot recovery.

The structured operations resource can request owned Applications or Status
refreshes using the existing worker pool. It reports accepted/running/terminal
state, retains bounded results across view disconnects, and can discard a
cancelled scan's eventual output. This is separate from cancellation of a reply
wait and does not stop a blocking backend call. See *FvwmMFL*(1) for typed
admission, generations, retention, notifications and explicit partial outcomes.

== ACTION PALETTE

*Super+A* opens the Action palette in the shipped desktop. The
*SlatePalette* function and *SendToModule FvwmDesktop palette* open the same
optional native Form. Super+P continues to open Run. The launcher also has an
Action palette entry. No extra process remains resident when the view closes.

The four labeled providers are managed windows, advertised desktops,
applications from the existing discovery owner, and eight registered actions:
Settings, Appearance, Configuration inspector, Check configuration, Refresh
applications, Terminal, Files and Run command. Windows marked SkipWindowList
are excluded. Desktops follow the core's advertised desktop inventory, rather
than the four default bar buttons. Provider availability is independent; a
failed core query leaves available applications and registered actions usable.
Each provider displays its state, retained count and failure or truncation
reason. Refresh (F5) requests a fresh core snapshot and application discovery.
While the view is open, native window add/configure/destroy/name and desk/page
events coalesce into refreshes. Its own Form updates are excluded. Closing
restores the ordinary desktop subscriptions. An unchanged palette does not poll
windows.

Type a query and press Filter (F3). Matching is literal and case insensitive
using the shared collection policy, with a maximum of 128 UTF-8 bytes. It is
not fuzzy matching or Unicode normalization. Tab and Shift-Tab move between
query and list. Arrows, Home/End and Page Up/Page Down move list focus; Enter
activates the focused result. Space toggles selection, but activation always
uses the focused row. Escape or Close returns focus through the normal FVWM
focus policy. Activating an action disables that Form's later focus return
before dispatch, so Form teardown cannot override the requested focus.

The native list reuses its windows during filtering and refresh, preserving the
query draft and surviving row selection, focus and scroll anchors. Native type
marks and explicit Window/Desktop/Application/Action text labels require no
image service or icon font. Printable Unicode labels are retained. Native configuration metacharacters
and controls are shown as [U+XXXX]; identity and filtering use the original
admitted text. Display labels
never become commands. A delayed callback from an older Form or list generation
is refused. Application activation rechecks its complete committed data identity
and generation; registered actions recheck current capabilities; core actions
revalidate the managed-window incarnation or advertised desktop before dispatch.

A bounded snapshot retains at most 512 windows, 128 desktops, 500 applications
and sixteen registered actions (eight currently). The core scans at most 4096
managed records and reports omitted inventory explicitly. Application discovery
can retain more entries for the ordinary launcher; the palette reports its own
500-entry cap. Core metadata is fetched in pages of at most sixteen rows.
Requests coalesce to one active and one latest pending refresh. Chunked replies,
query waits and native list publication are bounded. Missing native replies
close the view after five seconds; a core timeout marks its providers unavailable
and permits Refresh. The view closes after five minutes without a refresh.
Closing or reloading retires callbacks and releases the palette's core snapshot.
Submitting an action does not certify that a client has repainted.

For troubleshooting, *SendToModule FvwmDesktop palette-state token* emits
*Echo FVWM_PALETTE_STATE token hex-json* with open state, provider counts and
states, binding counters, native readiness and visible count. While open it
also emits *Echo FVWM_PALETTE_VIEW token hex-json* with query, view token,
native generation and total retained rows. Tokens follow the same bounded
identifier syntax as barrier. Every record fits the 1000-byte native command
limit; reading diagnostics neither refreshes nor activates the palette.
