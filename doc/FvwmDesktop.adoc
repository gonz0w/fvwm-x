== NAME

FvwmDesktop - FVWM-X baseline appearance and desktop services

== SYNOPSIS

Module FvwmDesktop

FvwmDesktop --check-config FILE [--json]

== DESCRIPTION

The sole shipped default configuration is the Slate desktop. Its layout is
shared by four palettes: Slate (teal), Dune (copper), Grove (green), and Ink
(blue). Each palette has matching light and dark colors and an original
wallpaper. Toolkit themes and settings are left alone.

The primary monitor has a flat top bar with application launcher, four
workspaces, window list, clock/calendar, status, appearance, and session
menus. Other monitors have no reserved bar space. Monitor topology events
rebuild the bar. Desktop workspaces are global and each has one page.

The centered launcher uses native FVWM menus with arrow-key navigation,
Enter, Escape and type-to-select. Search applications opens an input form
and then shows matching applications. It is a submitted search, rather than
a live fuzzy-search overlay. Discovery reads freedesktop desktop entries
without python-xdg, honors user overrides, Hidden, NoDisplay, OnlyShowIn,
NotShowIn and TryExec, and launches argument arrays rather than shell code.
Run command intentionally interprets the user's input with /bin/sh.

Files opens a native directory menu with folder navigation, a terminal
shortcut, and file opening. It shows up to 100 entries. An existing xdg-open
is used if available; otherwise files open in less in the configured terminal.
Calendar is a native month menu. Display information opens xrandr --query in
a terminal; this baseline does not yet include a graphical monitor editor.

== CONFIGURATION

Read the installed default-config/config to use the baseline. Normal FVWM
configuration lookup is unchanged; an existing personal config still wins.
The default reads $FVWM_USERDIR/local.config last for personal overrides.
No personal configurations are overwritten or removed.

Configuration examples for local.config:

....
*FvwmDesktop: palette slate
*FvwmDesktop: appearance auto
*FvwmDesktop: day 07:00
*FvwmDesktop: night 19:00
*FvwmDesktop: transparency on
*FvwmDesktop: motion off
*FvwmDesktop: keep_wallpaper off
*FvwmDesktop: terminal xterm
....

Explicit module configuration overrides saved preferences for the module's
lifetime. The settings center reports these overrides. Changing or resetting a
saved choice does not remove an explicit module option; remove that option and
restart the helper to use the saved choice.
Omit an option to let the Appearance menu remember its selection. Times use
local 24-hour HH:MM format and must be different. A day interval may cross
midnight. Automatic appearance is checked each minute and immediately on
startup or after the clock catches up following resume. This uses a session
helper, so it needs no cron entries or access to another session's DISPLAY.
Manual Light or Dark overrides the schedule until Auto is selected again.

The Appearance menu saves preferences as private, atomic JSON in
$FVWM_USERDIR/desktop-state.json. This file is data only, never executed as
configuration. Palette choices preserve layout and bindings. Keep current
wallpaper prevents palette and day/night changes from replacing the active
wallpaper. The retained palette wallpaper choice survives session restarts.
Custom wallpaper persistence remains the user's local.config responsibility.

== DESKTOP SETTINGS

The Appearance menu's Desktop settings entry opens a native FVWM menu. The
same registry supplies the menus, validation and settings queries. This first
configuration-center checkpoint covers the existing seven preferences only:

* *palette*, appearance group: slate; choices slate, dune, grove, ink.
* *appearance*, appearance group: auto; choices light, dark, auto.
* *keep_wallpaper*, appearance group: boolean, false.
* *day*, schedule group: local HH:MM, 07:00.
* *night*, schedule group: local HH:MM, 19:00.
* *transparency*, effects group: boolean, true.
* *motion*, effects group: boolean, false.

Times range from 00:00 to 23:59 and must differ. Use the schedule form or
the times command to change both together. Boolean set commands accept
true/false, on/off, yes/no or 1/0. Toggle changes the saved boolean choice.
Setting IDs and values map to fixed helper actions; they cannot contain FVWM
commands or resource paths. No focus, application or bar-layout settings are
registered in this checkpoint.

Each setting submenu shows its saved value, helper-effective value and source.
Saved means the helper's last successfully loaded or written snapshot; use
reload to adopt edits made outside the helper.
The effective value includes explicit *FvwmDesktop options. Application status
means the helper submitted its known commands to FVWM; it does not prove that
other modules have repainted. Later personal Style or Colorset commands cannot
be observed through this registry and are explicitly reported as unobserved.
The helper never rewrites personal FVWM configuration. Preview is unavailable:
timed confirmation, cancellation and restart recovery remain future work.

Choose Edit saved preferences from Appearance or Desktop settings to open the
native grouped editor. It presents the registry's choices and time fields, with
explicit module overrides shown beside the affected setting. The fields edit
saved preferences; an override still determines that setting's effective value.
Opening the editor and changing fields have no effect on the desktop or file.

Apply (F3) validates the entire selected scope and saves it with one atomic
replacement, then submits the resulting theme and closes the editor. A bad
value or failed write preserves the draft, file and effective preferences; a
native notice explains the refusal. Tab moves between time fields; Return moves
to the next time field. Click Apply or press F3 to apply from either field.
Defaults (F2) replaces the selected scope's draft with registered defaults without
saving. Cancel, Escape, closing the window or its five-minute deadline discards
the draft. The deadline uses elapsed time and does not extend while editing.

Only one settings editor belongs to a helper. Opening another replaces it.
An accepted set, toggle, times, reset or reload retires the old editor; restarting
the helper closes any predecessor's Form. Callback tokens belong to that editor
and settings generation, so delayed actions cannot apply an old draft to newer
state. External saved-file edits are still checked at Apply: reload and reopen
the editor to adopt them. Query generation is an opaque snapshot identity that
changes on successful preference publication/reload and helper restart; it is
not an X-server generation or evidence that arbitrary FVWM commands were observed.

Reset accepts one setting ID, group:appearance, group:schedule, group:effects
or all. It changes only those saved preferences to registered defaults. It
retains explicit module overrides and the current wallpaper when the effective
keep_wallpaper choice requests it. A reset that would make day and night equal
is refused; reset group:schedule to restore both times. Reload rereads the saved
file, validates the combined configuration and reapplies the theme.

FvwmMFL also exposes correlated settings queries, typed set/reset/reload and
non-publishing validation. A validation returns the proposed saved/effective
values for the observed provider/generation without writing, submitting a theme,
closing an editor or changing the generation. It checks combined values and
overrides; it does not promise that a later write can acquire the lock or pass
the current saved-file revision check. It is available to read-only IPC clients.
See *FvwmMFL*(1) for the exact versioned request syntax and lifecycle rules.
Cancelling an IPC wait does not cancel this helper's submitted action; query
before replaying a change whose result was lost.

Writes validate the complete candidate and replace a private file atomically
before changing the helper's state or submitting theme commands. A failed write
preserves the previous file and in-memory choices. Cooperating writers use a
nonblocking lock; a changed file is refused until reload. This is not a
transaction across FVWM, arbitrary user programs or storage-device failure.

The state file is capped at 8192 bytes and must be a regular file owned by the
current user, with one link and no group/other permissions. Its immediate
directory must be owned by the user, must not be a symlink, and must not be
group/other writable. The final file and lock cannot be symlinks or FIFOs.
Existing directory ancestry remains the user's chosen trust boundary. A
persistent private .desktop-state.lock is normal. Temporary files are removed
on failure; source configuration and unrelated files are left alone.

Unversioned JSON from earlier helpers is read using the original normalization
rules; the next successful change writes schema_version 1. Version 1 requires
the known fields and valid types. Unknown versions, duplicate fields, oversized
or invalid files are preserved. Startup uses defaults and reports a persistence
error; repair the data file or move it aside, then use reload-settings. The
helper does not silently overwrite unreadable or future-version state.

Transparency is enabled by default: the bar uses a retained root wallpaper
with a strong tint, and menus use FVWM's snapshot translucency. This works
without a compositor. It does not show live windows through the bar, blur
backgrounds, or fade client windows. Opaque mode resets the bar to a solid
surface and disables menu translucency. Motion is off by default; enabling
it adds FVWM submenu repositioning and window-shade steps. These are native
FVWM effects, not compositor fades.

The panel height and generic font are available as InfoStore values
slate_height and slate_font. Override them in local.config before startup.
The frame defaults use a 28-pixel title and flat vector buttons; local Style
and TitleStyle commands can change these independently. No proprietary or
icon fonts are required. PNG wallpaper decoding uses FVWM's optional PNG
support; builds without it retain solid palette backgrounds.

The running settings owner also serves FvwmMFL's versioned `settings` queries
and provider/generation-checked `set`, scoped `reset` and `reload` actions.
This exposes
the same registry, saved/effective values, override precedence and private-file
revision checks used by the native editor. See FvwmMFL's STRUCTURED REQUESTS
section for the wire format, bounds and result meanings. A committed preference
or submitted FVWM command is not completed core rendering. Helper generations
do not observe external Style/Colorset state; live preview remains unavailable.
The `ipc-request` module message is reserved for that bounded literal-data
transport; existing `query-settings` Echo consumers remain supported.

== CONFIGURATION CHECK

Desktop settings offers Check local.config. It reads
$FVWM_USERDIR/local.config in a bounded worker and presents a native report.
F1/F2 move between report pages; Escape closes the report. Source locations
include physical start/end lines for continued logical lines and the immediate
Read caller. Long paths are shortened for the native view. A new report replaces
the previous snapshot; callbacks from an older report cannot select its pages.

The check never executes configuration, starts modules, applies preferences,
expands variables or runs PipeRead, shell commands, functions or Lua. It checks
only literal colon-form *FvwmDesktop options for the seven registered settings,
plus literal Read filenames with optional Quiet. Boolean/time/enum validation
uses the same preference registry as the running helper. Explicit day/night
values must differ when both appear. Saved preferences are not loaded, so this
does not validate their combined effective runtime state.

Comments and blank lines are ignored. A backslash immediately before a newline
joins physical lines, as in FVWM's reader. Directive recognition and Read
separators use ASCII whitespace. Desktop options reuse the running helper's
existing trimming and literal-space option split. Input is UTF-8; other encodings
are reported as unchecked. NUL bytes are errors.

Literal Read searches FVWM_USERDIR, FVWM_DATADIR and the checker's working
directory, in that order, or uses an absolute path directly. It is not relative
to the including file. Quiet permits a missing optional file; it does not hide
an unreadable or nonregular source. Symbolic links are followed; device/inode
identity detects active Read cycles. Repeated nonrecursive reads remain allowed.
This is a fixed search-root snapshot, not a simulation of executable commands
that could change paths, variables or generated files.

Other FVWM commands, custom function calls, module options, terminal invocation,
expansions, escaped filenames and unsupported Read syntax are reported as
unchecked. They may be valid configuration. This first checker is not a full
FVWM syntax validator or a predictor of session startup; general core-command
argument/source diagnostics remain separate work. No configuration migration
or new desktop package is required.

For a complete source/include chain and observed file hashes, invoke the installed
helper directly outside FVWM, without an X display:

....
/path/to/FvwmDesktop --check-config "$HOME/.fvwm/local.config"
/path/to/FvwmDesktop --check-config "$HOME/.fvwm/local.config" --json
....

Use the helper in the configured ModulePath; it is normally installed in the
versioned libexec module directory. Text output escapes control characters in
paths. JSON schema_version 1 reports coverage, status, checked_directives,
errors, unchecked, observed files with SHA-256 hashes, and diagnostics. Each
diagnostic has path, line, end_line, included_from, severity, code, message and
parser. Included callers retain their own start/end lines. The file hashes
identify bytes read, not an atomic cross-file or future runtime snapshot.

Exit status 0 means the supported subset has no reported errors or unchecked
constructs. Status 1 means a supported-value or source-read error. Status 2
means incomplete coverage, an exhausted budget or CLI usage error. A zero exit
does not certify arbitrary FVWM configuration or effective runtime settings.

One check reads at most 4 MiB combined, 64 file visits, eight active file levels,
10,000 physical lines, 1 MiB per logical line and 64 diagnostics. Reaching a cap
reports incomplete checking. An elapsed three-second budget is checked between
reads/lines; it cannot preempt an individual filesystem call. Sources must be
regular files and are opened without blocking on FIFOs. No check writes a source
or preference file. The helper admits one check at a time within its existing
bounded worker pool and retains one result snapshot.

== DESKTOP SERVICES

The helper uses the Python runtime already required by FVWM, standard library
modules, and available OS tools. It never requires pip packages, dmenu,
stalonetray, an external notification daemon, ImageMagick, or a compositor.
Slow discovery, metrics and capture run outside the core event loop. Subprocess
queries have deadlines. Module queues, input packets and generated menus are
bounded; child programs do not inherit the module protocol descriptors.

Linux CPU/RAM counters come from /proc, and battery/link state from /sys.
FreeBSD and OpenBSD counters use sysctl and base utilities. RAM accounting is
used RAM including caches on BSD, and excludes available/reclaimable RAM on
Linux; the values are not directly comparable. Network status reports active
interfaces, not a guarantee of Internet access. Missing sensors show as not
reported; no battery is fabricated for a desktop machine.

Sound keys and menu actions use sndioctl on OpenBSD, mixer on FreeBSD, or an
already installed amixer on Linux. If the backend is absent, the sound menu
is disabled. Network information uses ifconfig or an existing ip command.
Settings needing privileges remain the operating system's responsibility.
No helper automatically invokes sudo or doas.

Screenshots use the existing Xlib library and Python's built-in PNG encoder.
Print captures the root display to ~/Pictures/Screenshots with a unique,
private filename. Capture supports TrueColor visuals and a maximum of 16
megapixels. The capture runs independently of the WM and does not include the
pointer cursor. A small native message announces the saved file or an error.
These messages report FVWM desktop actions; the helper is not a freedesktop
D-Bus application-notification server.

A terminal is detected from xterm, uxterm, or rxvt. Set FVWM_TERMINAL or the
terminal option for another command. Terminal tools require a compatible
-e option; no terminal is installed automatically.

Lock delegates only to an existing xlock or slock. If neither is available,
the Session menu disables Lock and a keyboard request explicitly reports
that the screen has NOT been locked. No decorative lock window is presented
as a security boundary. A portable bundled authentication locker remains
separate work. Power off and reboot require confirmation and use existing
session permissions; denied requests are reported. Log out quits FVWM;
Restart FVWM reloads it without closing application windows.

== KEYBOARD

Super+Space:: Centered application launcher.
Super+Enter:: Terminal.
Super+D:: Files.
Super+P:: Run command.
Super+L:: Request secure screen lock.
Super+1 through Super+4:: Select workspace.
Ctrl+F1 through Ctrl+F4:: Select workspace.
Alt+Tab:: Window list.
Alt+F4:: Close window.
Print:: Screenshot.
Volume keys:: Raise, lower, or mute available sound backend.
Super+left drag:: Move a window.
Super+right drag:: Resize a window.

The title bar moves a window when dragged and maximizes on double click.
Right-click the title for operations including sending to another workspace.
Right-click the desktop also opens the centered launcher.

== REMOTE COMMANDS

SendToModule FvwmDesktop accepts these commands:

....
set palette slate|dune|grove|ink
set appearance light|dark|auto
times 07:00 19:00
toggle transparency
toggle motion
toggle keep_wallpaper
settings [all|setting-ID|group:appearance|group:schedule|group:effects]
edit-settings [scope]
check-config
query-settings token [scope]
reset scope
reload-settings
refresh
discover
barrier token
terminal
files
calendar
screenshot
....

refresh reapplies the current theme and restores the clock/workspace display
after a bar rebuild. discover refreshes installed applications. A desktop
helper belongs to one FVWM session and has no network listener. barrier emits
Echo token after earlier helper commands reach FVWM. Tokens contain at most
64 letters, digits, underscores or hyphens. This orders command application;
independent modules may still be repainting.

settings opens the native configuration-center menu for the requested scope.
edit-settings opens the grouped saved-preference editor for the same scopes.
check-config starts the non-executing local.config check and accepts no module
arguments. The native report generates token-bound check-page callbacks;
ordinary clients should request a new check instead of reusing those callbacks.
The editor's apply-settings, defaults-settings and cancel-settings callbacks
carry an opaque per-instance token and are generated by the helper; ordinary
command clients should use the documented set, times, reset or reload commands.
query-settings emits one Echo message per registered setting and a final
completion message through the existing module transport. A token has 1 to 64
letters, digits, underscores or hyphens. Replies have this form:

....
desktop-settings-token setting-ID {JSON metadata and state}
desktop-settings-token done
....

Metadata includes type, default, choices or time bounds, description, group,
owner, capability, availability and preview support. State includes saved,
effective, source, application, generation and persistence_error. Each reply fits the
existing core command limit. Refused operations show a native notice and leave
the prior settings intact; this query is not the future general IPC result API.
persistence_error reports a startup read problem that blocks saving until a
successful reload; individual operation errors are reported by the notice.
