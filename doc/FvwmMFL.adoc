== NAME

FvwmMFL - the Fvwm3 front-loader module

== SYNOPSIS

_FvwmMFL_ can only be invoked by Fvwm3. Command line invocation of the
_FvwmMFL_ will not work.

This module has no command-line options.

== DESCRIPTION

The _FvwmMFL_ module provides access to Fvwm events over a unix-domain
socket. This module is intended to provide externally-written programs
(clients) the ability to receive information from Fvwm and to perform an
action on that event.

The information from Fvwm3 is in the form of JSON packets. Each JSON
packet has different fields, depending on the type requested.

== COMMUNICATION

The default unix-domain socket for _FvwmMFL_ is
*$TMPDIR/fvwmmfl/fvwm_mfl_$DISPLAY.sock*.

The path for where *fvwm_mfl_$DISPLAY.sock* is created can be changed by
setting the *FVWMMFL_SOCKET_PATH* environment variable.  _FvwmMFL_ will create
this if it does not exist, and set relevant permissions.

The lockfile in this directory must be a regular file owned by the current
user, with no group or other permissions and exactly one hard link. Symbolic
links and unsafe existing lockfiles are rejected. The default lockfile mode
is 0600. A rejected lockfile prevents this module from starting; the window
manager continues to run.
The private lockfile is retained after module shutdown so subsequent instances
lock the same inode. The socket is removed on normal signal-driven shutdown.

Commands are newline-delimited. A command may be split across socket writes;
it is executed only after the newline arrives. Empty lines are ignored.
Commands may contain at most 1000 bytes before the newline and must not contain
NUL bytes. An invalid command closes that client's connection.

The module accepts up to 32 concurrent clients. Each client has a 16 KiB input
buffer and a 256 KiB output queue; the shared command queue to FVWM is also
limited to 256 KiB. A client exceeding an output limit, or submitting a command
when the shared queue is full, is disconnected. Clients must read replies;
unwritten output has a 30-second inactivity timeout, and each incomplete
command must be completed within 30 seconds.
Idle subscriptions with no pending input or output remain connected.
A stalled connection to FVWM also has a 30-second write timeout.

== STRUCTURED REQUESTS

The connection profile advertises `request_version: 1` and
`request_prefix: "request "`. Existing text commands, subscriptions and event
objects keep their framing and behavior. A structured request is one line
beginning with the literal prefix `request ` followed by a JSON object:

....
request {"version":1,"id":"desktop-1","method":"query","resource":"desktop"}
....

The entire line, including the prefix and excluding its newline, has the same
1000-byte limit. Objects use the exact fields shown below; unknown or duplicate
fields, wrong types and invalid JSON are errors. IDs are strings of 1–64 ASCII
letters, digits, underscores, hyphens or periods. Embedded NUL escapes are
rejected, and JSON nesting is limited to four levels before parsing.

Replies are separate newline-delimited JSON objects, independent of event
subscriptions:

....
{"reply":{"version":1,"id":"desktop-1","status":"ok","result":{...}}}
{"reply":{"version":1,"id":"desktop-1","status":"error","error":{"code":"deadline_exceeded"}}}
....

An error has a null ID when the request has no safely recognized ID, duplicates
an outstanding ID, or is a refused legacy command. Clients dispatch replies by
ID and events by their existing keys. Local replies and subscribed events can
arrive before an earlier core query completes. Do not infer a reply boundary
from a socket write, or assume every record is a reply. Reuse an ID only after
receiving its terminal reply; a new connection has its own client-ID scope.

=== Queries

`method: "query"` requires `resource` and no additional fields:

* `capabilities` returns the supported methods/resources, pending and deadline
  limits, and truthful capability flags. Applied command results are unavailable;
  read-only admission is not a security boundary.
* `connection` returns this connection's `read_only` flag and selected event
  names. These are MFL-owned values and require no core round trip.
* `topology`, `workspaces`, `bindings`, `colorsets`, `appearance`, `menu-styles`
  and `decorations` query core-owned state, as described
  below. Binding pages also accept their documented continuation fields.
* `preview` queries or controls a core-owned runtime menu-opacity lease,
  as described below. Saved-preference preview remains separate.
* `pending` returns this connection's outstanding waits, as described below.
* `settings` queries the running FvwmDesktop settings owner, as described below.
* `files` discovers or queries running browser providers, as described below.
* `desktop` samples authoritative values through the existing core command
  engine and module-directed `Send_Reply`. It returns `scope:
  "core-current-monitor"`, `units: "actual-pixels"`, the current `desk`,
  `viewport` with x/y/width/height, `page` with x/y indices, and `work_area` with
  x/y/width/height. Rectangles are actual pixels; desk/page values are indices.
  The fields correspond to `$[desk.n]`, `$[vp.x]`, `$[vp.y]`, `$[vp.width]`,
  `$[vp.height]`, `$[page.nx]`, `$[page.ny]` and the four `$[wa.*]` variables.
  They preserve those variables' current-monitor/aggregate viewport semantics.
  Work area is the existing static work area, not the separate dynamic area.

The desktop query is an observation at core command evaluation, not a cached
second window-state authority or an atomic X-server transaction. It does not
provide the separate topology/binding views described below, shared core
preview generations or asynchronous action status. Helper-owned settings have their own
provider query and generation; they are not core window/theme state.

=== Core topology, workspace and binding queries

These read-only resources use the existing command engine and directed module
replies. They observe core-owned state at evaluation, without a second cache in
MFL, an X round trip, or executing configured binding actions:

....
request {"version":1,"id":"monitors-1","method":"query","resource":"topology"}
request {"version":1,"id":"workspaces-1","method":"query","resource":"workspaces"}
request {"version":1,"id":"bindings-1","method":"query","resource":"bindings","limit":8}
....

`topology` returns `state: "observed"`, `scope: "committed-topology"`,
`units: "actual-pixels"`, `root_fallback`, and the existing committed `topology`
with its `monitors` array. Each monitor includes `name`, `name_atom`, `primary`,
`geometry` (x/y/width/height), `physical_mm` (width/height) and output XIDs.
`epoch` is an exact 16-character lowercase hexadecimal string, avoiding loss in
JSON consumers with double precision numbers. It identifies topology commits
within a core lifetime; it is not a shared theme/window generation or a promise
that the X server has not changed since the last successful acquisition.
A root-sized `FVWM-X-Root` monitor with no outputs is the explicit fallback when
RandR exposes no monitors. A missing committed snapshot returns `unavailable`.

`workspaces` returns `state: "observed"`, `scope: "core-monitors"`, actual-pixel
units, `desktop_mode` (`global`, `shared` or `per-monitor`) and a `monitors` array.
Each record has its core monitor `name`, current `desk`, `viewport` with x/y and
aggregate desktop width/height, page-grid counts in `pages`, `scale_quarters`,
and separate static `work_area` and `dynamic_work_area` rectangles. Desk/grid
values are indices/counts; scale is the number of quarter steps per logical
unit. These records follow the core's retained monitor collection; they do not
replace the committed physical topology.

`work_area_freshness: "cached"` is explicit. Work areas sample existing core
caches without scanning windows or forcing publication. An all-zero rectangle
cannot distinguish an uninitialized cache from an empty area at the origin;
it is returned as JSON null (unknown). Other rectangles retain actual pixels,
including zero dimensions at a nonzero origin. This does not certify freshness,
recompute root EWMH work areas or change reservations. Normal window/geometry
processing updates those caches. Separate query evaluations are not an atomic
transaction across topology, workspace state and X properties.

`bindings` returns `state: "observed"`, `scope: "global-bindings"`, opaque
`generation`, `offset`, `bindings` and `next_offset`. It describes installed
Key, PointerKey and mouse records, including separate native records for a key
that maps to multiple keycodes. Omit `scope` or use `scope: "global"` for
these records. The other binding scopes are described below. No scope certifies
which binding wins for a particular application or event.

Each entry contains `type` (`Key`, `PointerKey`, `MousePress`, `MouseRelease`),
`code` (keycode or button), `key` (configured key name or null), native
`context_mask`, raw X modifier `modifier_mask`, literal `action`, and optional
window match pattern in `window` (null when unrestricted). JSON strings escape
control characters and replace malformed UTF-8 at presentation; no text from a
query result is evaluated as a command. Numeric context masks use FVWM's context
bits; modifier masks retain the configured X11 mask, including AnyModifier.

Binding pages default to offset 0 and limit 8. `limit` must be an integer from
1 to 16; `offset` an integer from 0 to 4096. Use the returned `next_offset` and
48-character lowercase hexadecimal `generation` for continuation; null ends
the list. A nonzero offset requires that generation. For example, after a page
returns offset 8 and token G, request the next page with `offset: 8` and
`generation: G` (substitute the exact observed string). An optional generation
on offset 0 makes that first page conditional too. Continue with the same scope;
offsets refer to records in that scope, not across all lists.

Every binding command conservatively invalidates pages, including unbind and
commands that ultimately make no global binding change. A change to
`IgnoreModifiers` also invalidates every binding scope; repeating the same
modifier policy does not. All scopes share this conservative token. It belongs
to the core incarnation, so a restarted core cannot accept a predecessor's page.
A mismatch returns `stale_generation`; restart from offset 0. An offset beyond
the current list returns `invalid_offset`. A revision exhausted or unavailable
returns `generation_unavailable`. Paging copies only the requested records and
retains no binding pointers/cursors between commands.

The `scope` field selects one of five binding observations, advertised in the
capabilities result's `binding_scopes`:

....
request {"version":1,"id":"menu-1","method":"query","resource":"bindings","scope":"menu","limit":8}
request {"version":1,"id":"defaults-1","method":"query","resource":"bindings","scope":"menu-fallback","limit":8}
request {"version":1,"id":"placement-1","method":"query","resource":"bindings","scope":"placement"}
request {"version":1,"id":"policy-1","method":"query","resource":"bindings","scope":"policy"}
....

`menu` returns `scope: "menu-bindings"` with the regular menu list.
`menu-fallback` returns `scope: "menu-fallback-bindings"` with the permanent
startup defaults. Both use the same entry schema, bounds and paging as global
bindings. The core checks regular menu bindings first and falls back only if
none matches. An override does not delete its fallback; removing the regular
binding can expose that default again. These are separate lists, not a merged
list of winners. Menu records retain native keycodes with `key: null` because
the menu owner does not retain the original key spelling. Empty lists are valid.

`placement` returns `scope: "placement-bindings"`, `generation`,
`button_count`, `drag_finish_mask` and `interactive_finish_mask`. These are the
current normalized finish controls used for placement/move interactions, not
a history of configured commands. Bit zero represents mouse button 1; a set
bit selects its normal finish path; a cleared bit selects cancellation. Existing
initial-placement/resize and already-held-button rules still apply. Clearing all
placement buttons and then setting button 3 to PlaceWindowDrag returns drag
mask 4. `key_bindings: false` and `modifier_bindings: false` describe the
existing placement parser's restrictions; this query does not add bindings.

`policy` returns `scope: "binding-policy"`, `generation`, named `contexts`
and X11 `modifiers` maps, `ignored_modifier_mask` from IgnoreModifiers,
`xkb_ignored_modifier_mask` for the build's ignored XKB state bits, and
`used_modifier_mask` for standard X modifiers after those exclusions. Context
maps include individual areas/title buttons and composite `menu_item`, `frame`,
`sidebar` and `all`; composite entries overlap. Modifier `any` is AnyModifier,
not a bit to OR into a specific modifier combination. This metadata helps
interpret raw records; it does not resolve window matching, keysym lookup,
menu precedence or a hypothetical event's winning action.

Placement and policy are whole scalar snapshots: they reject `offset` and
`limit` even when zero/default, and have no `bindings` list or `next_offset`.
An optional exact generation makes either conditional. Unknown scopes, wrong
types and unsupported fields return `invalid_request`; a well-formed obsolete
generation returns `stale_generation`. Querying never changes grabs, placement
controls, modifier policy, menus or binding generations.

Core snapshots share the eight pending slots and absolute five-second deadline,
read-only admission, local pending inspection and wait-only cancellation.
Capabilities advertise the 32,768-byte decoded result maximum, binding page and
offset limits. Each result is assembled in at most 128 ordered 256-byte chunks
from directed `MX_REPLY`, with incarnation/serial correlation. Settings replies
keep their separate 8192-byte maximum. Malformed core fragments return
`invalid_core_reply`; late/cancelled/disconnected assemblies are discarded.
No native packet type or layout changes.

A topology/workspace query permits at most 64 monitor records, with at most 64
outputs and 256 name bytes per topology monitor. Binding key names have the
same 256-byte bound; actions and window patterns permit 1024 bytes. A scan skips
at most 4096 bindings and copies at most 16. Limits or an oversized serialized
snapshot return `query_too_large` without partial success or silent truncation;
try a smaller binding page when appropriate. These transport limits do not
restrict existing configuration files. Allocation failure returns
`allocation_failed` when a reply can still be queued; otherwise the ordinary
deadline/disconnect policy applies. Wider providers, domain progress/cancellation
and shared-core preview/recovery remain separate capabilities.

=== Runtime menu-opacity preview

The `preview` resource owns one core-wide runtime lease for an existing named
menu style's opacity. It does not write saved preferences or preview complete
themes, colorsets, fonts, decorations or arbitrary command strings. Capability
fields report `preview_scope: "menu-opacity"`, `preview_persistence:
"runtime-only"`, `preview_lease_limit: 1` and `preview_timeout_max_ms: 30000`.

First query `appearance` for its 48-character generation, then submit:

----
request {"version":1,"id":"try-opacity","method":"action","resource":"preview","operation":"start","generation":"CURRENT_48_HEX_TOKEN","target":"SlateLauncherStyle","values":{"opacity":70},"timeout_ms":15000}
request {"version":1,"id":"preview-state","method":"query","resource":"preview"}
request {"version":1,"id":"undo-opacity","method":"action","resource":"preview","operation":"revert","generation":"PREVIEW_48_HEX_TOKEN","target":"LEASE_48_HEX_TOKEN"}
----

Replace the uppercase placeholders with returned lowercase tokens. `start`
requires one `values` member, integer `opacity` from 0 through 100, and an
existing literal menu-style name of 1 through 64 UTF-8 bytes. The optional
integer `timeout_ms` is 1000 through 30000; default 15000. The core checks the
appearance generation and captures/applies the scalar in one command. A stale
start returns `stale_generation`; an active lease returns `preview_busy`.
No separate query-to-command race authorizes restoration.

A successful start returns `scope: "menu-opacity"`, `state: "active"`, `lease`,
post-apply `generation`, `target`, `previous_opacity`, `preview_opacity`,
`remaining_ms` and `recovery: "pending"`. It explicitly reports `persistence:
"not-attempted"` and `rendered_completion: "unknown"`. Opacity is sampled at
menu presentation; close and reopen the menu to inspect it. Already displayed
pixels can retain their preceding presentation.

Use `operation: "confirm"` with the same lease and post-apply generation to
keep the runtime value, or `revert` to restore the exact previous scalar.
Confirm returns `state: "confirmed"`, `recovery: "kept"`; explicit recovery
returns `state: "reverted"`, `recovery: "restored"`. Confirmation never writes
preferences. A later theme/configuration update or WM restart can replace it.
Terminal states have zero remaining time. A completed lease refuses further
confirmation/revert with `preview_finished`; an old or foreign lease returns
`preview_unavailable`. Wrong current lease generations return `stale_generation`.

Only the originating connection can inspect/control its record. Other
connections observe `state: "inactive"` without lease/target values. One
terminal record is retained until replacement or native producer retirement;
there is no preview history service. Lease/view identities also isolate stale
callbacks across reconnects and core/helper incarnations. They are correlation
identities, not an X11 authorization boundary.

The monotonic core deadline restores without client polling. Disconnect queues
an ordered abandon behind an admitted start; native producer death restores
before its core record retires. A full output queue may delay/drop abandon;
the independent deadline remains responsible. Recovery also runs during menu
and pointer interactions, changing only the scalar, without freeing borrowed
menu resources. It runs at the next eligible core service point and cannot
preempt a single blocking command or a stalled X server.

Any intervening tracked appearance activity conservatively ends the lease as
`conflicted`, `recovery: "refused-conflict"`. It preserves the newer state,
including target deletion; confirm/revert return `preview_conflict`. Inspect
current policy before trying again. Unrelated tracked activity can also refuse
restore. There is no blind fallback command or persistent rollback file.
Allocation/clock/revision/target refusal is explicit; an uncertain or cancelled
request wait does not cancel a submitted start. Query the originating connection
or allow its core deadline to settle. Read-only connections can query but cannot
start/confirm/revert; switching mode does not disable existing recovery.

=== Appearance configuration, menu styles and decorations

Three read-only core observations support inspection of shared appearance policy:

----
request {"version":1,"id":"theme-state","method":"query","resource":"appearance"}
request {"version":1,"id":"menu-policy","method":"query","resource":"menu-styles","limit":8}
request {"version":1,"id":"decor-policy","method":"query","resource":"decorations","limit":8}
----

`appearance` returns `state: "observed"`,
`scope: "core-appearance-configuration"`, an opaque 48-character `generation`,
and `coverage`. The generation tracks activity in window-style definition,
decoration definition, menu-style policy, DefaultFont, and colorset owners.
It advances conservatively on admitted changes, including commands that fail or
leave identical values. Colorset allocation, parse, asynchronous settlement and
publication also advance it. Existing binding and colorset tokens keep their
independent resource scope. Automatic window retirement advances the token
only when it removes a WindowStyle definition; explicit destroy commands still
invalidate conservatively. Repeated observations preserve the appearance token.

Style/WindowStyle/FocusStyle and destruction share their existing definition
owner, including recursive functions. Decoration initialization/destruction,
title/button/border styles and ButtonState are tracked. MenuStyle parsing,
copying and removal share menu-policy hooks. This tracks those configuration
owners, not every visible change on the display. Per-window assignments,
interactive state, menu contents, image pixels/resources inside decorations,
client changes and compositor state are not an effective appearance snapshot.
The response explicitly reports `window_effective_state: false`,
`rendered_completion: "unknown"`, `conditional_application: false` and
`preview_supported: false`.

An optional `generation` on `appearance` must match exactly, or the query returns
`stale_generation`. The scalar resource rejects `scope`, `target`, `offset` and
`limit`. Observing a matching token does not make a later command conditional:
a producer or image completion can intervene. Do not use a separate query and
mutation as a rollback guard. The separate `preview` resource below owns an
atomic snapshot/apply/recovery operation for one menu-opacity scalar. The
appearance query flags do not advertise general appearance transactions.

`menu-styles` and `decorations` use that same conservative appearance token.
They return `state: "observed"`, `generation`, `offset`, `next_offset`, and a
`menu_styles` or `decorations` array. Default offset is 0 and limit is 8; limits
are 1 through 16. Nonzero offsets require the previous generation. The final
next offset is null. Restart at offset zero after `stale_generation`;
`invalid_offset` refuses a position beyond the collection. Continuations beyond
4096 return `query_too_large`. Traversal and serialization are bounded; records
and cursors are never retained between requests. Scope/target fields are rejected.

Both page resources describe definition order with the default record first.
Each entry has a literal `name` and `default` flag. Names/templates are data and
are not evaluated. `units: "configuration-pixels"` distinguishes configured
measurements from scaled on-screen geometry; no effective window/menu layout is
computed. A decoration's unavailable name is null rather than an invented ID.

Menu policy includes submenu `animation`, `opacity_percent` (100 is opaque),
`border_width`, normalized `popup_delay_10ms` and `popdown_delay_10ms`,
`automatic_hotkeys`, `submenus_left`, nullable `item_format`, and the menu,
active, greyed and title `colorsets`. These are registered policy fields;
actual drawing and assigned menus have separate lifetimes. Decoration entries
include configured `title_height`, `minimum_title_height`,
`title_justification` (center/left/right/unknown), and `button_slots`. A zero
configured height leaves sizing to the existing font/minimum policy. Faces,
paths, resource handles, callback owners and window assignments are omitted.

No query adds an X round trip or changes definitions. Existing message/result,
queue, deadline, cancellation and read-only limits apply. Tokens are
process/resource observations, not authentication or persistent identifiers;
`generation_unavailable` refuses an unavailable/exhausted revision. A colorset
or unrelated covered definition change can conservatively invalidate either
page resource even when its selected entries remain identical.

=== Core colorset inspection

`query` with `resource: "colorsets"` observes the core's existing sparse colorset
records. It does not allocate missing IDs, parse commands, read image files or
query the X server. Read-only connections can use all three forms:

----
request {"version":1,"id":"palette-list","method":"query","resource":"colorsets","limit":8}
request {"version":1,"id":"palette-one","method":"query","resource":"colorsets","target":"21"}
request {"version":1,"id":"palette-summary","method":"query","resource":"colorsets","scope":"summary"}
----

Each result has `state: "observed"`, `scope: "core-colorsets"`, an opaque
48-character `generation`, `total`, configured `record_limit`, and `page_max: 16`.
The scalar summary omits entries and cursors. Use it to check a previous
observation without transferring palette records. It accepts an optional
`generation`; a mismatch returns `stale_generation`, rather than an unchanged
response. Summary requests reject `target`, `offset` and `limit`.

Inventory pages default to offset 0 and limit 8; limits are 1 through 16.
`colorsets` contains at most that many records in the core registry order.
`offset` and `next_offset` are ordinal positions, not colorset IDs. Follow
`next_offset` with the returned generation; nonzero offsets require it. The
last page has a null next offset. Offsets are bounded at 4096; a configured
larger registry can report `query_too_large` when continuation would exceed that
bound. Its summary and exact-ID lookups remain available. An offset beyond the
current collection returns `invalid_offset`.

`target` is a canonical decimal string from `"0"` through `"2147483647"`.
It selects exactly one existing ID, including sparse high IDs; no default-zero
fallback is applied. Unknown IDs return `unavailable`. Target requests reject
`offset`, `limit` and `scope`, accept an optional generation, and return a
one-entry `colorsets` array with `targeted: true` and null cursors. Inventory
results have `targeted: false`.

Entry `pixels` contains foreground, background, hilight, shadow,
foreground_shadow, tint and icon_tint as exact 16-digit hexadecimal strings.
`pixel_encoding: "colormap-hex"` means X colormap pixel values, not RGB strings,
portable colors, pointers or pixmap IDs. No RGB conversion is performed.
`opacity_percent` distinguishes foreground, image and icon opacity. Entries also
report tint percentages, dithering, shape presence and background presence,
type, dimensions and transparency (`none`, `parent` or `root`). Dimensions use
actual pixels. Paths, parser text and resource ownership pointers are omitted.

`values: "published"` refers to the retained colorset used by rendering/modules.
`update_state` is `idle`, `pending` or `refused` for the owner's separate image
preparation. A refused replacement can leave the previous palette published;
`idle` does not certify that a screen repaint has completed. Commands, newly
allocated records and asynchronous image/effect settlements conservatively
invalidate the colorset generation, even when final values do not change.
Repeated queries preserve it. Tokens identify this core incarnation and this
resource only; they are neither authentication nor a persistence identifier.
`generation_unavailable` refuses an exhausted/unavailable token.

A query is a synchronous core observation; subsequent commands or asynchronous
settlements can change it. On stale pages, restart at offset zero. These tokens
do not cover Style/decorations, window policy or all appearance changes, and
cannot authorize rollback after a separate check. `preview_supported: false`
keeps colorset preview/revert unavailable. The separate runtime `preview`
resource owns only a menu-opacity scalar. Existing settings generations retain
their separate scope.

=== Browser metadata and selection

The optional Go browser registers one opaque 32-character lowercase hexadecimal
`provider` identity per connection. Discover up to eight running instances:

....
request {"version":1,"id":"browsers","method":"query","resource":"files"}
request {"version":1,"id":"folder","method":"query","resource":"files","provider":"PROVIDER_32_HEX","scope":"state"}
request {"version":1,"id":"selected","method":"query","resource":"files","provider":"PROVIDER_32_HEX","scope":"selection","limit":8}
....

Discovery returns `version: 1`, `query_only: true`, `provider_limit: 8` and
`providers`, each with `provider` and `busy`. An empty list means no registered
browser. Targeted queries require `provider` and `scope`: `state`, `items`,
`selection` or `properties`. Read-only connections may query; registration is
refused in read-only mode. This is same-user metadata transport, not an X11 or
same-user security boundary. Use matching browser/MFL builds.

Each successful targeted result contains `version: 1`, `provider`, opaque
32-character `generation`, `scope` and `observed: true`. The browser reconciles
its current native selection/focus before answering, without submitting a user
action or replacing its native windows. Draft input and file content are absent.

* `state` returns base64 `path_bytes`, loaded/visible/selected counts, focused
  ID, filter/sort/view/watch state and `page_max: 8`, `selection_limit: 256`,
  `actions: false`, `file_content: false`. It does not enumerate a new directory.
* `items` pages the current visible order. `selection` pages the selected set,
  including filtered-out selections. Both return `items`, `total`, `offset` and
  integer-or-null `next_offset`. Items contain opaque `id`, base64 `name_bytes`,
  a clipped display `label`, `kind`, symbolic `mode`, decimal-string
  `size_bytes` and `mtime_ns`, plus `selected` and `focused`. Labels are not paths;
  preserve raw bytes and parse the decimal strings for exact 64-bit integers.
* `properties` returns a `properties` object with selected count, files,
  directories, links, special entries and decimal-string `regular_file_bytes`.
  `recursive` and `links_followed` are false. Folder contents, link targets and
  file content are not read. An empty selection is unavailable.

For pages, optional `limit` is 1–8 (default 8); `offset` is 0–4096. A nonzero
offset requires the preceding result's `generation`. Metadata, projection,
selection or focus changes invalidate that token with `stale_generation`;
restart from offset zero. `state` and `properties` reject paging fields.
Tokens are scoped to the selected provider incarnation. Observed metadata can
be older than the filesystem; it is not authority to mutate or open a path.

MFL routes one query at a time to each producer's own connection, with no Echo
broadcast or second metadata cache. The existing eight waits per client and
five-second absolute deadline apply. A busy producer returns `provider_busy`;
a missing/disconnected owner returns `provider_unavailable`. Cancellation or a
waiter disconnect discards its result but retains the producer slot until the
terminal response or owner disconnect. This bounds queued work even when a
producer stalls. Malformed producer replies disconnect that producer. Responses
are limited to 8192 assembled bytes; larger observations return
`result_too_large`, so request a smaller page where applicable.

Producer registration uses `method: "register", resource: "files", provider`.
Identity cannot change on that connection; reconnect to retire it. Dedicated
`file_query` records carry version, 16-hex serial, provider, scope, generation,
offset and limit. Matching producers reply with reserved
`files_reply SERIAL part INDEX HEX` lines and `files_reply SERIAL end COUNT`,
using ordered chunks of at most 256 bytes and 32 parts. The assembled object
contains `result` or `error: {code: ...}`. Other connections and old serials
cannot complete the active producer response. These are internal producer
messages, not user commands. Typed actions, file mutation and protected clipboard
payload transport remain outside this query interface.

=== Desktop settings provider

With FvwmDesktop running, query its registered settings through the same
correlated request transport:

....
request {"version":1,"id":"settings-1","method":"query","resource":"settings"}
request {"version":1,"id":"schedule-1","method":"query","resource":"settings","scope":"group:schedule"}
....

Optional `scope` defaults to `all`. It accepts one registered key or
`group:appearance`, `group:schedule` and `group:effects`, matching FvwmDesktop's
existing settings scopes. The result identifies `owner: "FvwmDesktop"`,
`schema_version: 1`, opaque `provider` and `generation` tokens, `saved_revision`
and a `settings`
object keyed by setting name. Each item includes its type/default/choices or
range, description, saved/effective values, override source and capability.
The provider token identifies one helper incarnation. An optional `provider`
field targets a query to that exact instance; omit it to discover an owner.
The generation belongs to this helper's settings snapshot; it changes after
accepted settings changes, reload or helper restart.

Typed actions use `method: "action"`, `resource: "settings"`, `operation` and
the exact provider and generation returned by the preceding query:

....
request {"version":1,"id":"apply-1","method":"action","resource":"settings","operation":"set","provider":"0123456789abcdef0123456789abcdef","generation":"0123456789abcdef0123456789abcdef","values":{"palette":"grove","motion":false}}
request {"version":1,"id":"reset-1","method":"action","resource":"settings","operation":"reset","provider":"0123456789abcdef0123456789abcdef","generation":"0123456789abcdef0123456789abcdef","scope":"group:effects"}
request {"version":1,"id":"reload-1","method":"action","resource":"settings","operation":"reload","provider":"0123456789abcdef0123456789abcdef","generation":"0123456789abcdef0123456789abcdef"}
....

Both tokens are 32 lowercase hexadecimal characters; use the observed values.
Only the selected provider responds, so multiple FvwmDesktop instances cannot
race another owner's refusal against a successful commit. If that provider
exits/restarts, requests to its old identity reach the deadline: rediscover with
an untargeted query before choosing the new owner. `set`
accepts a nonempty `values` object with at most eight registered keys and
typed string/boolean/integer values. Numeric transport values must be integral
and fit signed 32-bit bounds; the owner enforces each setting's range.
`launcher_opacity` accepts 0 through 100, default 94. It validates the complete combined change before
publishing, so day/night schedules can change atomically. `reset` requires a
scope; `reload` accepts no scope or values. Unknown/duplicate fields, nested
values, missing tokens and wrong types are refused. A stale generation
returns `stale_generation` without mutation. Existing module overrides still
take precedence over saved preferences.

FvwmDesktop retains its private atomic file replacement, nonblocking writer
lock and saved-file revision check. Invalid values return `invalid_value`;
unavailable/refused file persistence or reload returns `persistence_failed`.
For an external file change, reload/query before intentionally trying again.
Successful set/reset returns `state: "committed"`; reload returns `state:
"reloaded"`; query returns `state: "observed"`. Results include the new
generation and a settings snapshot (reset returns its selected scope).

`application: "submitted-to-fvwm"` means commands were queued by the owner;
`asynchronous_completion: "unknown"` remains explicit. If publication succeeds
but command submission fails, the result retains its committed/reloaded state
with `application: "submission-failed"`. It does not report an unchanged state
or invite blind replay. Generic `applied_command_results` remains false; this
provider observes its own saved preferences, not final core rendering.
Saved-preference preview remains unavailable (`preview: false`). The separate
core `preview` resource changes only runtime menu opacity. The opacity registry
entry reports `native_preview: true` for its native Keep and save consumer;
`runtime_constraint: "transparency-disabled"` explains opaque-mode masking.
This adds no generic IPC saved-preview operation. See FvwmDesktop for file
schema migration and separate runtime-confirmation/persistence outcomes.

Capabilities name the settings provider with availability `on-request`; MFL
does not start it, retain a second settings cache or infer liveness from a core
barrier. Before initial module configuration completes, the provider returns
`provider_not_ready` without exposing provisional defaults or executing typed
actions/validation. Retry a query after a bounded delay; do not automatically
replay actions. An absent/stalled provider reaches `deadline_exceeded`. A timeout or
disconnect can occur after an action commits: query after reconnecting rather
than infer refusal or automatically replay the action.

Settings requests share the eight pending slots and absolute five-second
deadline. The normalized provider input is limited to 384 bytes, excluding
client IDs and outer envelope; larger input returns `request_too_large`.
The internal reply is at most 8192 decoded bytes in 32 ordered chunks. Partial,
malformed or out-of-order replies return `invalid_provider_reply`; expiry and
disconnect release assembly storage. A restart cookie plus nonreused serial
prevents late replies from completing a replacement request or MFL process.
Typed data travels hex-encoded through existing directed module messages, so
setting values cannot become FVWM expansions or command syntax. This is
correlation and literal-data framing, not peer authentication on shared X11.
If a future registry exceeds the reply bound, the result can omit `settings`
with `settings_unavailable: "reply_too_large"`; query a smaller scope. An
already committed action retains its outcome and generation.

=== Observe the desktop provider

The `provider` resource currently describes the configured FvwmDesktop preference
owner. It shares settings' bounded directed request/reply transport:

....
request {"version":1,"id":"owner-1","method":"query","resource":"provider"}
request {"version":1,"id":"owner-2","method":"query","resource":"provider","provider":"0123456789abcdef0123456789abcdef"}
....

Omitting `provider` discovers an instance; if several are running, the first
reply wins. This is not an inventory of all instances. Use the returned exact
32-character lowercase hexadecimal provider identity for subsequent requests.
The result includes `owner: "FvwmDesktop"`, `schema_version: 1`, `provider`,
settings `generation`, `resources: ["settings"]`, supported `operations`,
`notifications: "invalidation-only"` and `preview: false`.

`lifecycle_scope: "desktop-preferences"` limits `lifecycle` to initial module
configuration: `starting` with `availability: "configuring"`, or `ready` with
`availability: "available"`. Unlike settings queries, this query can report
starting before END_CONFIG_INFO. Availability does not promise a successful
future file write. `persistence_error` reports a known settings-load problem;
`failure_reason` is otherwise null. Actions still recheck their generation,
values and persistence conditions. `application_completion: "unknown"` and
`service_lifecycle: false` are explicit: this does not manage session services,
confirm painted state, infer process death or certify a power/locker backend.
An absent/stalled provider or obsolete target reaches `deadline_exceeded`.

To avoid fetching unchanged preference metadata, a settings query may include
both its exact provider and last observed generation:

....
request {"version":1,"id":"preferences-2","method":"query","resource":"settings","provider":"0123456789abcdef0123456789abcdef","generation":"0123456789abcdef0123456789abcdef","scope":"all"}
....

If the preference generation matches, the result contains `state: "unchanged"`,
`scope`, identity/generation and `snapshot_required: false`, with no `settings`.
If it differs, return the usual complete observed result for that scope. Scope
validation still runs; malformed tokens or generation without provider are
refused. The token identifies saved/effective preferences, not repaint,
application submission, external file changes, clock-driven theme appearance or
liveness. A client needs its own valid cache for the requested scope; the helper
does not know which earlier fields that client retained.

Opt into preference invalidations with `watch`; `unwatch` removes the interest:

....
request {"version":1,"id":"watch-1","method":"watch","resource":"provider"}
request {"version":1,"id":"watch-2","method":"watch","resource":"provider","provider":"0123456789abcdef0123456789abcdef"}
request {"version":1,"id":"stop-watch","method":"unwatch","resource":"provider"}
....

One watch belongs to each connection. A later watch replaces its filter; omit
provider to observe all FvwmDesktop instances or supply one exact identity.
Unwatch accepts no provider filter. Both methods work in read-only mode and
at pending-request capacity without consuming a slot. Their correlated results
have `state: "watching"`/`"unwatched"`, the filter as `provider` (or null), and
`snapshot_required` true/false. Connection queries expose `provider_watch` and
`provider_filter`. This interest is independent of legacy set/unset event flags.

After configuration readiness and accepted preference changes/reload, watchers
receive a separate JSON record, without preference values or action text:

....
{"provider_changed":{"version":1,"owner":"FvwmDesktop","provider":"0123456789abcdef0123456789abcdef","generation":"fedcba9876543210fedcba9876543210","snapshot_required":true}}
....

Treat each notice as invalidation, not an applied-action result or authoritative
snapshot. Register the watch first, then query a fresh snapshot; the watch
acknowledgement always requires that query. A notice can interleave with replies.
If a notice races a query, fetch again before trusting cached values. Reconnects
lose the watch and all history: re-register and query. No event replay, provider
cache or subscription history is retained by MFL. Startup of a replacement
helper announces its new identity to unfiltered watchers; an exact old-identity
filter cannot discover its replacement. Helper death itself produces no notice;
use bounded queries and SESSION's future lifecycle contract for that distinction.

Malformed internal notices cannot safely identify an owner. Interested clients
instead receive `provider_invalidated` with version 1, owner FvwmDesktop,
`reason: "malformed_notice"` and `snapshot_required: true`; discard the affected
cache and query again. Notices use the same bounded per-client output queue as
other events. An unqueueable/slow consumer disconnects independently; it must
resnapshot after reconnecting. There is no unbounded notification backlog or
authority to roll back a submitted change. Existing shared-X/local-peer trust
limits still apply; tokens and notices are not authentication.

=== Owned desktop background operations

FvwmDesktop can own correlated refresh operations for its existing application
catalog and status collector. Provider queries advertise `operation_targets:
["applications", "status"]`, operation limit 16 and terminal retention 300000 ms.
These scans use the existing two-worker pool and four-job admission limit.
Other legacy desktop jobs share that limit; duplicate target work returns
`operation_busy` without admitting a new attempt. No file mutation, arbitrary
command, power transition or generic job loader is added.

....
request {"version":1,"id":"refresh-1","method":"action","resource":"operations","operation":"start","provider":"0123456789abcdef0123456789abcdef","generation":"0123456789abcdef0123456789abcdef","target":"applications"}
request {"version":1,"id":"jobs-1","method":"query","resource":"operations","provider":"0123456789abcdef0123456789abcdef"}
request {"version":1,"id":"job-1","method":"query","resource":"operations","provider":"0123456789abcdef0123456789abcdef","target":"fedcba9876543210fedcba9876543210"}
....

Start requires the current provider/preference generation as an admission guard.
The result contains owner/provider, `disconnect: "continue"` and an `operation`
record. Its generated `id` differs from the connection's request ID. The record
has its own generation, target, state, `cancel_requested`, unknown progress
(`completed`/`total` null and `unit: "unknown"`), application outcome, result,
error, `worker_stop: "unknown"`, `rollback: false` and remaining `retention_ms`.
No field promises a total or percentage the backend cannot report.

States are accepted, running, completed, failed and cancelled. Fast work can
skip an observed running state. Completed means the worker returned and its
normal menu/status commands were submitted; it does not confirm core application
or repaint. Application refresh results report entry count; status results
report that a sample object was collected, including potentially unavailable
metrics. Worker failure reports `worker_failed` with no publication. Publication
failure reports `publication_failed` and `application: "partial-or-unknown"`;
commands or in-memory changes can already have occurred. No rollback is inferred.
Errors do not broadcast worker exception text, paths, labels or result payloads.
These targets request no decisions; unsupported operations remain explicit errors.

Query without target returns at most 16 compact operation summaries plus declared
limits; target selects one full record. Active records have null retention time.
Terminal records expire after five monotonic minutes, or earlier when the next
admission needs space and evicts the oldest admitted terminal record. They are
memory-only and vanish on helper restart. Missing/expired IDs return
`operation_unavailable`; a retired provider identity times out. No result archive
or reconnect replay is retained by MFL.

Cancellation is a domain action distinct from cancelling the MFL reply wait:

....
request {"version":1,"id":"cancel-job","method":"action","resource":"operations","operation":"cancel","provider":"0123456789abcdef0123456789abcdef","generation":"0123456789abcdef0123456789abcdef","target":"fedcba9876543210fedcba9876543210"}
....

Here generation is the operation record's latest generation, not the preference
generation used to start. A mismatch returns `stale_generation` without changing
the operation; an already terminal record returns `operation_finished`. A queued
future may cancel immediately. A running/computed future remains admitted with
`cancel_requested: true` until it returns, then its output is discarded and the
record becomes cancelled. This cannot interrupt one blocking scan/system call,
prove worker stoppage or undo prior effects. These two backends only collect data;
this cancellation contract does not apply to later file/session operations.
Read-only connections can observe operations but cannot start or cancel them.

Closing a client continues owned work and retains its record within those bounds.
Reconnect, rediscover the provider and query the retained list/ID. A lost start
reply or cancelled reply wait must not be blindly replayed: the helper may have
admitted an operation. There is no cross-reconnect deduplication key or exactly-
once execution claim. Each admitted record has one terminal outcome while retained.

`watch`/`unwatch resource: "operations"` opts into operation invalidations with
an optional provider filter, independently of the preference watch. Each client
has at most one watch per resource; capabilities advertise both limits. Local
watch admission is read-only and consumes no pending slot. Connection queries
expose `operation_watch` and `operation_filter`. Watch then query a fresh snapshot.

....
{"operation_changed":{"version":1,"owner":"FvwmDesktop","provider":"0123456789abcdef0123456789abcdef","id":"fedcba9876543210fedcba9876543210","generation":"0123456789abcdef0123456789abcdef","state":"completed","snapshot_required":true}}
....

Intermediate observations coalesce to at most one notice per retained record
per owner poll; terminal invalidation is sent before admission can evict that
record. Results remain queryable under the declared retention, not inside events.
Malformed internal notices produce `operations_invalidated` with version 1,
reason malformed_notice and snapshot_required true. Queries/replies/events can
interleave. The existing bounded queue disconnects unqueueable clients, who must
resnapshot after reconnect. No history, progress flood cache, value broadcast,
process-death inference or authentication boundary is introduced.

=== Validate settings without saving

Use `method: "validate"`, `resource: "settings"`, the observed `provider` and
`generation`, and the same nonempty typed `values` object as a set action:

....
request {"version":1,"id":"check-1","method":"validate","resource":"settings","provider":"0123456789abcdef0123456789abcdef","generation":"0123456789abcdef0123456789abcdef","values":{"palette":"grove","motion":false}}
....

No `operation` or `scope` field is accepted. The owner uses the same complete
candidate validation as a commit, including combined day/night values and module
overrides. The result has `state: "validated"`, the unchanged base generation
and candidate `settings` with proposed saved/effective values. Each candidate
item and the result have `application: "not-submitted"`; `persistence:
"not-attempted"`, `asynchronous_completion: "not-started"` and `preview: false`
are explicit. No file is written, theme command submitted, editor retired or
generation changed. Read-only connections can validate.

Validation is not a live preview, reservation or promise that persistence will
succeed. It does not lock/read-check the saved file or test permissions, space
or external changes. A known persistence error remains in item metadata but
does not prevent value validation. A later set still checks its generation,
current private-file revision and writer lock. Query again after conflicts.
Invalid values and stale generations use the same errors as set actions.

=== Inspect and cancel pending waits

Local lifecycle requests remain available when all eight pending slots are full
or the core/provider is stalled, including on read-only connections:

....
request {"version":1,"id":"waits-1","method":"query","resource":"pending"}
request {"version":1,"id":"cancel-1","method":"cancel","target":"apply-1"}
....

The query returns `scope: "connection"`, `execution: "unknown"` and a `requests`
array of at most eight entries. Each has its client `id`, `resource`, `operation`,
`remaining_ms` and wait `state`: `awaiting-reply`, `receiving-reply` for a partial
provider assembly, or `deadline-reached` while terminal expiry is due. These
are transport observations; they do not describe domain progress, work totals,
provider liveness or whether an action has committed. Local queries themselves
are not stored. No other connection's requests or completed history is exposed.

A cancel requires only `target`, with the same syntax/limit as a client ID.
Use a fresh cancel request ID. If the target is still waiting, MFL sends its
terminal `wait_cancelled` error first, frees its slot/partial assembly, then
replies to the cancel with `state: "wait-cancelled"`, `target`, `execution:
"unknown"` and `rollback: false`. Other pending waits keep their deadlines.
Late target replies are discarded; the original ID/slot can be reused after its
terminal reply. Internal serials prevent old results from completing the new
wait. A missing, completed, expired or foreign target returns
`request_not_pending`; no retained history distinguishes those cases. If expiry
is already due, the original receives `deadline_exceeded`, not `wait_cancelled`.
The ordinary duplicate-outstanding-ID rule applies to cancel request IDs too.

Cancellation stops this connection's wait. It does not retract a queued command,
stop the helper's action or undo a saved preference. An action may commit before
or after cancellation. Query the owner before deciding what to do next; do not
blindly replay. Disconnect also drops waits without cancelling domain execution.
Capabilities advertise `cancellation: "wait-only"`; domain cancellation,
progress/decision protocols and reconnect result recovery remain unavailable.

=== Processed stream barrier

A request with `method: "barrier"` has no resource or mode field:

....
request {"version":1,"id":"ordered-1","method":"barrier"}
....

Its successful result is `{"state":"processed","asynchronous_completion":"unknown"}`.
The core has reached this point in MFL's command stream, preserving existing
producer ordering after previously forwarded commands. Commands from other
clients can be interleaved; there is no multi-client transaction. The result
does not certify that a previous command was valid, applied successfully,
painted, persisted or completed an asynchronous process/service. It is not an
applied-action acknowledgement. Domain-specific action results remain separate.

=== Read-only admission

A connection can narrow its future admission once:

....
request {"version":1,"id":"restrict-1","method":"set_mode","mode":"read-only"}
....

The result returns the connection state. Repeating this mode is harmless;
changing back to writable is unsupported. Queries, validation, wait cancellation, barriers and event
subscriptions remain usable. Typed settings actions receive a correlated
`read_only` error. Other legacy commands, including global debug
changes, receive an uncorrelated `read_only` error and are not forwarded.
Already queued commands are not undone. A newly connected client starts in the
existing writable mode, so callers should set this mode before sending actions.

This is an accidental-authority reduction for a cooperating connection. The
same user can reconnect, use other clients or access the X display; this mode
is not an X11 sandbox, authentication mechanism or confidentiality boundary.
The existing private socket permissions remain unchanged.

=== Bounds, errors and disconnects

Each client can have eight outstanding core/provider requests. Each has an
absolute five-second monotonic deadline that unrelated traffic cannot extend.
Local queries remain available while core requests wait. Duplicate outstanding
IDs return `duplicate_id` with a null ID; an additional request returns
`too_many_requests` with its own ID. A full shared output queue returns
`core_queue_full` before that request is forwarded.

A terminal `deadline_exceeded` releases the slot but does not retract commands
already queued to the core. Late replies are discarded using internal serials
that are never reused within the module process. Disconnect destroys the
connection's pending state; replies from an older connection cannot complete a
replacement connection's request. There is no replay or retained result store.
On module/core disconnection, pending callers must treat unreceived results as
unavailable and query again after reconnecting, rather than infer success.

Other error codes are `invalid_request`, `unsupported_version`,
`unsupported_method`, `unsupported_resource`, `unsupported_mode`,
`invalid_core_reply` and `request_ids_exhausted`. Malformed stream framing still
closes the offending connection under the existing framing rules. Allocation,
queue-delivery or timer-setup failure can close it without a terminal record.
All replies share the existing bounded client output queue and write deadline;
a stalled reader is disconnected without blocking healthy clients.

== REGISTERING INTEREST

Commands can be sent to _FvwmMFL_ to control which information is sent
the client. The _set_ command is used for this. The table below shows
which events can be subscribed to.

[cols="<,<",]
|===
|_Event_ |_Description_
|new_window |Fired when a new window is mapped and visible.
|map |Fired when a window is mapped.
|configure_window |Fired when a window is moved or resized.
|destroy_window |Fired when a window is closed.
|new_page |Fired when a new page is switched to.
|new_desk |Fired when a new desk is switched to.
|raise_window |Fired when a window is raised (or changes layer).
|lower_window |Fired when a window is lowered (or changed layer).
|focus_change |Fired when a window loses/gains focus.
|enter_window |Fired when a window has the pointer moved into it.
|leave_Window |Fired when a window has pointer moved out of it.
|window_shade |Fired when a window is shaded.
|window_unshade |Fired when a window is unshaded.
|window_name |Fired when the window name changes.
|visible_name |Fired when the visible window name changes.
|res_class |Fired when the class of the window is set.
|res_name |Fired when the resource of the window is set.
|iconify |Fired when a window is iconified.
|deiconify |Fired when a window is deiconified.
|icon_name |Fired when the icon name changes.
|visible_icon_name |Fired when the icon's visible name changes.
|icon_file |Fired when the path to the icon changes.
|icon_location |Fired when the icon location changes.
|restack |Fired when the window stacking order changes.
|echo |Fired when Fvwm receives an Echo command.
|===

For example, to register an interest in _new_window_ and _focus_change_,
the following commands would be set via the socket:

....
set new_window
set focus_change
....

To remove interest in an event, use the _unset_ command:

....
unset focus_change
....

== JSON FORMAT

Each packet sent to a client is in plain JSON. The information contained
in each packet varies depending on the event.
String values and object keys use UTF-8. Each invalid byte is printed as
`\ufffd` (the replacement character U+FFFD). Valid UTF-8 is preserved.
This output conversion does not change stored FVWM text or native module packets.
