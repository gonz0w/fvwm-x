== NAME

FvwmMFL - the Fvwm3 front-loader module

== SYNOPSIS

_FvwmMFL_ can only be invoked by Fvwm3. Command line invocation of the
_FvwmMFL_ will not work.

This module has no command-line options.

== DESCRIPTION

The _FvwmMFL_ module provides access to Fvwm events over a unix-domain
socket. This module is intended to provide externally-written programs
(clients) the ability to receive information from Fvwm and to perform an
action on that event.

The information from Fvwm3 is in the form of JSON packets. Each JSON
packet has different fields, depending on the type requested.

== COMMUNICATION

The default unix-domain socket for _FvwmMFL_ is
*$TMPDIR/fvwmmfl/fvwm_mfl_$DISPLAY.sock*.

The path for where *fvwm_mfl_$DISPLAY.sock* is created can be changed by
setting the *FVWMMFL_SOCKET_PATH* environment variable.  _FvwmMFL_ will create
this if it does not exist, and set relevant permissions.

The lockfile in this directory must be a regular file owned by the current
user, with no group or other permissions and exactly one hard link. Symbolic
links and unsafe existing lockfiles are rejected. The default lockfile mode
is 0600. A rejected lockfile prevents this module from starting; the window
manager continues to run.
The private lockfile is retained after module shutdown so subsequent instances
lock the same inode. The socket is removed on normal signal-driven shutdown.

Commands are newline-delimited. A command may be split across socket writes;
it is executed only after the newline arrives. Empty lines are ignored.
Commands may contain at most 1000 bytes before the newline and must not contain
NUL bytes. An invalid command closes that client's connection.

The module accepts up to 32 concurrent clients. Each client has a 16 KiB input
buffer and a 256 KiB output queue; the shared command queue to FVWM is also
limited to 256 KiB. A client exceeding an output limit, or submitting a command
when the shared queue is full, is disconnected. Clients must read replies;
unwritten output has a 30-second inactivity timeout, and each incomplete
command must be completed within 30 seconds.
Idle subscriptions with no pending input or output remain connected.
A stalled connection to FVWM also has a 30-second write timeout.

== STRUCTURED REQUESTS

The connection profile advertises `request_version: 1` and
`request_prefix: "request "`. Existing text commands, subscriptions and event
objects keep their framing and behavior. A structured request is one line
beginning with the literal prefix `request ` followed by a JSON object:

....
request {"version":1,"id":"desktop-1","method":"query","resource":"desktop"}
....

The entire line, including the prefix and excluding its newline, has the same
1000-byte limit. Objects use the exact fields shown below; unknown or duplicate
fields, wrong types and invalid JSON are errors. IDs are strings of 1–64 ASCII
letters, digits, underscores, hyphens or periods. Embedded NUL escapes are
rejected, and JSON nesting is limited to four levels before parsing.

Replies are separate newline-delimited JSON objects, independent of event
subscriptions:

....
{"reply":{"version":1,"id":"desktop-1","status":"ok","result":{...}}}
{"reply":{"version":1,"id":"desktop-1","status":"error","error":{"code":"deadline_exceeded"}}}
....

An error has a null ID when the request has no safely recognized ID, duplicates
an outstanding ID, or is a refused legacy command. Clients dispatch replies by
ID and events by their existing keys. Local replies and subscribed events can
arrive before an earlier core query completes. Do not infer a reply boundary
from a socket write, or assume every record is a reply. Reuse an ID only after
receiving its terminal reply; a new connection has its own client-ID scope.

=== Queries

`method: "query"` requires `resource` and no additional fields:

* `capabilities` returns the supported methods/resources, pending and deadline
  limits, and truthful capability flags. Applied command results are unavailable;
  read-only admission is not a security boundary.
* `connection` returns this connection's `read_only` flag and selected event
  names. These are MFL-owned values and require no core round trip.
* `settings` queries the running FvwmDesktop settings owner, as described below.
* `desktop` samples authoritative values through the existing core command
  engine and module-directed `Send_Reply`. It returns `scope:
  "core-current-monitor"`, `units: "actual-pixels"`, the current `desk`,
  `viewport` with x/y/width/height, `page` with x/y indices, and `work_area` with
  x/y/width/height. Rectangles are actual pixels; desk/page values are indices.
  The fields correspond to `$[desk.n]`, `$[vp.x]`, `$[vp.y]`, `$[vp.width]`,
  `$[vp.height]`, `$[page.nx]`, `$[page.ny]` and the four `$[wa.*]` variables.
  They preserve those variables' current-monitor/aggregate viewport semantics.
  Work area is the existing static work area, not the separate dynamic area.

The desktop query is an observation at core command evaluation, not a cached
second window-state authority or an atomic X-server transaction. It does not
provide the complete monitor topology, configured bindings, shared core preview
generations or asynchronous action status. Helper-owned settings have their own
provider query and generation; they are not core window/theme state.

=== Desktop settings provider

With FvwmDesktop running, query its registered settings through the same
correlated request transport:

....
request {"version":1,"id":"settings-1","method":"query","resource":"settings"}
request {"version":1,"id":"schedule-1","method":"query","resource":"settings","scope":"group:schedule"}
....

Optional `scope` defaults to `all`. It accepts one registered key or
`group:appearance`, `group:schedule` and `group:effects`, matching FvwmDesktop's
existing settings scopes. The result identifies `owner: "FvwmDesktop"`,
`schema_version: 1`, opaque `provider` and `generation` tokens, `saved_revision`
and a `settings`
object keyed by setting name. Each item includes its type/default/choices or
range, description, saved/effective values, override source and capability.
The provider token identifies one helper incarnation. An optional `provider`
field targets a query to that exact instance; omit it to discover an owner.
The generation belongs to this helper's settings snapshot; it changes after
accepted settings changes, reload or helper restart.

Typed actions use `method: "action"`, `resource: "settings"`, `operation` and
the exact provider and generation returned by the preceding query:

....
request {"version":1,"id":"apply-1","method":"action","resource":"settings","operation":"set","provider":"0123456789abcdef0123456789abcdef","generation":"0123456789abcdef0123456789abcdef","values":{"palette":"grove","motion":false}}
request {"version":1,"id":"reset-1","method":"action","resource":"settings","operation":"reset","provider":"0123456789abcdef0123456789abcdef","generation":"0123456789abcdef0123456789abcdef","scope":"group:effects"}
request {"version":1,"id":"reload-1","method":"action","resource":"settings","operation":"reload","provider":"0123456789abcdef0123456789abcdef","generation":"0123456789abcdef0123456789abcdef"}
....

Both tokens are 32 lowercase hexadecimal characters; use the observed values.
Only the selected provider responds, so multiple FvwmDesktop instances cannot
race another owner's refusal against a successful commit. If that provider
exits/restarts, requests to its old identity reach the deadline: rediscover with
an untargeted query before choosing the new owner. `set`
accepts a nonempty `values` object with at most the seven registered keys and
typed string/boolean values. It validates the complete combined change before
publishing, so day/night schedules can change atomically. `reset` requires a
scope; `reload` accepts no scope or values. Unknown/duplicate fields, nested
values, missing tokens and wrong types are refused. A stale generation
returns `stale_generation` without mutation. Existing module overrides still
take precedence over saved preferences.

FvwmDesktop retains its private atomic file replacement, nonblocking writer
lock and saved-file revision check. Invalid values return `invalid_value`;
unavailable/refused file persistence or reload returns `persistence_failed`.
For an external file change, reload/query before intentionally trying again.
Successful set/reset returns `state: "committed"`; reload returns `state:
"reloaded"`; query returns `state: "observed"`. Results include the new
generation and a settings snapshot (reset returns its selected scope).

`application: "submitted-to-fvwm"` means commands were queued by the owner;
`asynchronous_completion: "unknown"` remains explicit. If publication succeeds
but command submission fails, the result retains its committed/reloaded state
with `application: "submission-failed"`. It does not report an unchanged state
or invite blind replay. Generic `applied_command_results` remains false; this
provider observes its own saved preferences, not final core rendering.
Live preview remains unavailable (`preview: false`).

Capabilities name the settings provider with availability `on-request`; MFL
does not start it, retain a second settings cache or infer liveness from a core
barrier. An absent/stalled provider reaches `deadline_exceeded`. A timeout or
disconnect can occur after an action commits: query after reconnecting rather
than infer refusal or automatically replay the action.

Settings requests share the eight pending slots and absolute five-second
deadline. The normalized provider input is limited to 384 bytes, excluding
client IDs and outer envelope; larger input returns `request_too_large`.
The internal reply is at most 8192 decoded bytes in 32 ordered chunks. Partial,
malformed or out-of-order replies return `invalid_provider_reply`; expiry and
disconnect release assembly storage. A restart cookie plus nonreused serial
prevents late replies from completing a replacement request or MFL process.
Typed data travels hex-encoded through existing directed module messages, so
setting values cannot become FVWM expansions or command syntax. This is
correlation and literal-data framing, not peer authentication on shared X11.
If a future registry exceeds the reply bound, the result can omit `settings`
with `settings_unavailable: "reply_too_large"`; query a smaller scope. An
already committed action retains its outcome and generation.

=== Processed stream barrier

A request with `method: "barrier"` has no resource or mode field:

....
request {"version":1,"id":"ordered-1","method":"barrier"}
....

Its successful result is `{"state":"processed","asynchronous_completion":"unknown"}`.
The core has reached this point in MFL's command stream, preserving existing
producer ordering after previously forwarded commands. Commands from other
clients can be interleaved; there is no multi-client transaction. The result
does not certify that a previous command was valid, applied successfully,
painted, persisted or completed an asynchronous process/service. It is not an
applied-action acknowledgement. Domain-specific action results remain separate.

=== Read-only admission

A connection can narrow its future admission once:

....
request {"version":1,"id":"restrict-1","method":"set_mode","mode":"read-only"}
....

The result returns the connection state. Repeating this mode is harmless;
changing back to writable is unsupported. Queries, barriers and event
subscriptions remain usable. Typed settings actions receive a correlated
`read_only` error. Other legacy commands, including global debug
changes, receive an uncorrelated `read_only` error and are not forwarded.
Already queued commands are not undone. A newly connected client starts in the
existing writable mode, so callers should set this mode before sending actions.

This is an accidental-authority reduction for a cooperating connection. The
same user can reconnect, use other clients or access the X display; this mode
is not an X11 sandbox, authentication mechanism or confidentiality boundary.
The existing private socket permissions remain unchanged.

=== Bounds, errors and disconnects

Each client can have eight outstanding core queries/barriers. Each has an
absolute five-second monotonic deadline that unrelated traffic cannot extend.
Local queries remain available while core requests wait. Duplicate outstanding
IDs return `duplicate_id` with a null ID; an additional request returns
`too_many_requests` with its own ID. A full shared output queue returns
`core_queue_full` before that request is forwarded.

A terminal `deadline_exceeded` releases the slot but does not retract commands
already queued to the core. Late replies are discarded using internal serials
that are never reused within the module process. Disconnect destroys the
connection's pending state; replies from an older connection cannot complete a
replacement connection's request. There is no replay or retained result store.
On module/core disconnection, pending callers must treat unreceived results as
unavailable and query again after reconnecting, rather than infer success.

Other error codes are `invalid_request`, `unsupported_version`,
`unsupported_method`, `unsupported_resource`, `unsupported_mode`,
`invalid_core_reply` and `request_ids_exhausted`. Malformed stream framing still
closes the offending connection under the existing framing rules. Allocation,
queue-delivery or timer-setup failure can close it without a terminal record.
All replies share the existing bounded client output queue and write deadline;
a stalled reader is disconnected without blocking healthy clients.

== REGISTERING INTEREST

Commands can be sent to _FvwmMFL_ to control which information is sent
the client. The _set_ command is used for this. The table below shows
which events can be subscribed to.

[cols="<,<",]
|===
|_Event_ |_Description_
|new_window |Fired when a new window is mapped and visible.
|map |Fired when a window is mapped.
|configure_window |Fired when a window is moved or resized.
|destroy_window |Fired when a window is closed.
|new_page |Fired when a new page is switched to.
|new_desk |Fired when a new desk is switched to.
|raise_window |Fired when a window is raised (or changes layer).
|lower_window |Fired when a window is lowered (or changed layer).
|focus_change |Fired when a window loses/gains focus.
|enter_window |Fired when a window has the pointer moved into it.
|leave_Window |Fired when a window has pointer moved out of it.
|window_shade |Fired when a window is shaded.
|window_unshade |Fired when a window is unshaded.
|window_name |Fired when the window name changes.
|visible_name |Fired when the visible window name changes.
|res_class |Fired when the class of the window is set.
|res_name |Fired when the resource of the window is set.
|iconify |Fired when a window is iconified.
|deiconify |Fired when a window is deiconified.
|icon_name |Fired when the icon name changes.
|visible_icon_name |Fired when the icon's visible name changes.
|icon_file |Fired when the path to the icon changes.
|icon_location |Fired when the icon location changes.
|restack |Fired when the window stacking order changes.
|echo |Fired when Fvwm receives an Echo command.
|===

For example, to register an interest in _new_window_ and _focus_change_,
the following commands would be set via the socket:

....
set new_window
set focus_change
....

To remove interest in an event, use the _unset_ command:

....
unset focus_change
....

== JSON FORMAT

Each packet sent to a client is in plain JSON. The information contained
in each packet varies depending on the event.
String values and object keys use UTF-8. Each invalid byte is printed as
`\ufffd` (the replacement character U+FFFD). Valid UTF-8 is preserved.
This output conversion does not change stored FVWM text or native module packets.

== EXAMPLE

The following example shows how to monitor for _focus_change_ events at
the shell, printing the JSON returned:

....
  echo set focus_change | nc -U /tmp/fvwm_mfl.sock 2>&1 | jq --unbuffered
....

Outputs:

....
{ "focus_change": { "window": "0x5400022", "type": 0, "hilight": {
"text_colour": 16777215, "bg_colour": 32767 } } }
....
